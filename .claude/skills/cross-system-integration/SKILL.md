# ข้อมูลถึงปลายทางเมื่อ "นับแถวในฐานของเขา" ได้ — ไม่ใช่เมื่อ POST ได้ 200

> **ที่มา: 20–21 พ.ย. 2569** — ต่อ CEO AI Thailand เข้ากับ Marketing OS (คนละโค้ดเบส คนละ Supabase)
> รอบแรก **สำเร็จทุกชั้นที่ตรวจ** แล้วยังผิด: โค้ดถูก · เทสต์ผ่าน · CI เขียว · deploy เขียว ·
> POST 200 · แถวเข้าฐานจริง — แต่เข้า **ฐานของเราเอง** ไม่ใช่ฐานที่แอปปลายทางอ่าน
> รอบสองถึงจะถึงจริง และรู้ว่าถึงเพราะ **นับแถวในฐานของเขาก่อน-หลัง** ไม่ใช่เพราะอ่านโค้ด

---

## กฎเดียวที่อยู่เหนือทุกข้อ

> ### "ฐานที่เราเขียนลง" ต้องเท่ากับ "ฐานที่ผู้อ่านอ่านอยู่"
> ถามข้อนี้ **ก่อนเขียนโค้ดบรรทัดแรก** · ตอบไม่ได้ = ถามเจ้าของ ห้ามเริ่ม

`shipped-not-written` ถามว่า *"โค้ดเราถูกเรียกใช้ไหม"* — ตัวนี้ถามต่อว่า **"แล้วของที่ส่งไป มีใครอ่านไหม"**
จำนวนการตรวจไม่ได้แปลว่าตรวจครบ ถ้าไม่เคยตรวจ **ข้อต่อ**

---

## ด่าน 0 — ปลายทางที่แท้จริง (ทำก่อนทุกอย่าง)

| ต้องรู้ | วิธีตรวจ (ห้ามเดาจากชื่อ) |
|---|---|
| endpoint นี้ deploy อยู่บน project ไหน | อ่าน config ของ endpoint เอง ไม่ใช่เดาจากชื่อฟังก์ชัน |
| มันเขียนลงฐานไหน | ดู `SUPABASE_URL`/connection ที่ **ตัวมัน** ใช้ |
| แอปที่จะอ่าน ชี้ไปฐานไหน | ถามเจ้าของ หรืออ่าน env ของแอปนั้น |
| ฐานปลายทางมีตารางนั้นจริงไหม | query `information_schema` ของ **ฐานนั้น** |

🔴 **เคสจริง**: `marketing-track` ชื่อเหมือนของระบบการตลาด แต่ deploy บน project ของเรา
ใช้ `SUPABASE_URL` ของตัวเอง ⇒ เขียนลงฐานเรา · ฐานที่แอปเขาอ่าน **ไม่มีตารางนั้นเลย**
⇒ ท่อเปิดอยู่ ~3 เดือน ได้ 0 แถว โดยไม่มีใครรู้

⚠️ **ห้ามอ่านสคีมาฝั่งหนึ่งแล้วเดาอีกฝั่ง** — ชื่อตารางขึ้นต้นเหมือนกันไม่ได้แปลว่าเป็นชุดเดียวกัน

---

## ด่าน 1 — วัดค่าตั้งต้นก่อนทดสอบเสมอ

```sql
-- ก่อนทดสอบ
select count(*), max(created_at) from <ตารางปลายทาง>;
-- ทดสอบ
-- หลังทดสอบ: นับซ้ำด้วยคำสั่งเดิม
```

🔴 **"มีแถวอยู่" ≠ "แถวนี้มาจากเรา"** — เคสจริง: ปลายทางมี 1 แถวอยู่ก่อนแล้ว (ของเขาเองเมื่อสัปดาห์ก่อน)
ถ้าไม่วัดค่าตั้งต้น จะอ่านว่า "ทำงานแล้ว" ทั้งที่ของเรายังไม่เคยถึง
หลังทดสอบได้ 5 ⇒ **ของเรา = 4** และต้องไล่ดูทีละแถวว่า `name/topic/format` ตรงตารางแมปไหม

⚠️ นับด้วย **คำสั่งเดียวกันเป๊ะ** ทั้งก่อนและหลัง · เปลี่ยนเงื่อนไขกลางทาง = เทียบไม่ได้

---

## ด่าน 2 — env ที่อ่านตอน build (จุดที่เงียบที่สุด)

🔴 **`vars.X` กับ `secrets.X` เป็นคนละที่เก็บ** — ชี้ผิดที่ = ค่าว่าง **เงียบสนิท ไม่มี error**
และบรรทัดนั้น **ถูกไวยากรณ์ทั้งสองแบบ** ⇒ ไม่มีเทสต์ไหนในรีโปจับได้เลย

🔴 **"ตั้งค่าแล้ว" ≠ "ค่าเข้าแล้ว"** — ค่าถูกอ่านตอน build ⇒ ตั้งเสร็จต้อง **deploy ใหม่** ค่าถึงจะอยู่ในไฟล์ที่เบราว์เซอร์โหลด

**พิสูจน์ได้ทางเดียว — ดูของที่ผู้ใช้โหลดจริง:**
```bash
curl -s https://<โดเมน>/ | grep -oE '/assets/index-[A-Za-z0-9_-]+\.js'
curl -s https://<โดเมน>/assets/index-XXXX.js | grep -c '<ค่าที่ควรอยู่ในนั้น>'
```
เจอ = เข้าแล้ว · ไม่เจอ = **ยังไม่เข้า (ยังเงียบ ไม่ใช่พัง)**
⚠️ เช็กชื่อไฟล์ hash ด้วยว่า **เปลี่ยนจากรอบก่อน** — ไม่งั้นอาจกำลังอ่านบันเดิลเก่า

**ต้องไม่ลืมตรวจของเดิมด้วย**: ถ้า secret อื่นถูกแก้ในช่วงเดียวกัน ให้ grep ยืนยันว่าค่าเดิมยังอยู่
(ค่าที่หาย = ระบบพังเงียบ ๆ และรู้ตัวตอนมีคนเข้าไม่ได้)

## ด่าน 3 — คีย์

🔴 **ห้ามฝังคีย์/JWT ลงรีโปเด็ดขาด** แม้เป็น `anon` ที่ public โดยดีไซน์ — env เท่านั้น
🔴 **ก่ออ้างว่า "เราทำแบบนี้อยู่แล้ว" ต้อง `grep` ให้เห็นของจริงในรอบนั้น**
   เคสจริง: อ้างว่า "คีย์ของเราก็อยู่ในรีโป" เพื่อให้เหตุผลกับการฝัง JWT — **เท็จ** ของเราเป็นคนละรูปแบบ
   และคนที่จับได้คือเครื่องสแกนความลับ ไม่ใช่ตัวเอง
🟢 **ตรวจ role ของ JWT ที่ขึ้น production จริง** — ถอด payload ดู `role`/`ref` ต้องเป็น `anon` ของ project ที่ตั้งใจ
   **ห้ามมี `service_role` ในของที่เบราว์เซอร์โหลดได้เด็ดขาด**

**กลไกที่ต้องทิ้งไว้**: เทสต์ห้ามรูปแบบ JWT ทั้งรีโป + สแกนบันเดิลหลัง deploy

---

## ด่าน 4 — สคีมาของเขาแคบกว่าของเราเสมอ

อ่าน **CHECK / enum ตัวจริง** ของเขาก่อนแมป ห้ามอ่านจากเอกสาร
🔴 **ที่แมปไม่ได้ ห้ามเดาให้ลงช่อง** — ต้องมีรายการ **"ไม่แมป + เหตุผลรายข้อ"** และเทสต์บังคับว่า
ทุกค่าต้องอยู่กองใดกองหนึ่ง (แมปแล้ว / ไม่แมปเพราะ X) **ห้ามเงียบ**

⚠️ **ข้อมูลที่บิดให้ลงช่องได้ แย่กว่าข้อมูลที่ไม่ส่ง** — ไม่ส่ง = รู้ว่าไม่มี · บิด = เชื่อผิดตลอดไป

🟢 เจอข้อบกพร่องในโมเดลของเขาได้ ให้บอก/แก้ (ถ้าได้รับอนุญาต) **แบบ additive เท่านั้น**
เคสจริง: เขามีเสาสาร 7 แต่ CHECK รับ 4 ⇒ 3 เสาของเขาเองวัดไม่ได้ · ขยายเป็น 7 แล้วอ่านกลับมายืนยัน

---

## ด่าน 5 — ความยินยอมไม่ใช่ค่าคงที่ในสคีมา

ถ้าสคีมาปลายทางบังคับฟิลด์ทำนอง `consent: 'analytics_opt_in'` — **นั่นคือคำประกาศแทนผู้ใช้**
ส่งทั้งที่เขาไม่ได้ยินยอม = โกหก + ผิด PDPA
⇒ **fail-closed ทุกกรณีที่ไม่ชัด**: ยังไม่เลือก · เลือก "จำเป็นเท่านั้น" · อ่าน storage ไม่ได้ = **ไม่ส่ง**
⇒ ด่านต้องจับ **จุดเรียกใช้** ไม่ใช่ชื่อฟังก์ชัน (ไม่งั้นเทสต์ไปเจอตัวนิยามในไฟล์เดียวกันแล้วผ่านฟรี)

---

## ด่าน 6 — ปล่อย `test` ก่อน `live`

- origin allowlist ของเขามักมีแค่โดเมน production ⇒ **ทดสอบจากเครื่องไม่ได้** ต้องทดสอบบน production ด้วยโหมด test
- flag โหมดต้อง **ถูกล็อกด้วยเทสต์** — เปลี่ยนเป็น live ต้องแก้เทสต์ด้วย = ตั้งใจ ไม่ใช่เผลอ
- ตรวจที่บ้านก่อนยิง: ก้อนที่ผิดข้อเดียวมักทำให้ **ทั้งก้อน** ตก ⇒ ทำ validator ที่สะท้อนสคีมาเขาครบ
  (จำนวน · คีย์เกิน · ขนาด · ช่วงเวลา · id ซ้ำ)

---

## ด่าน 7 — ก่อนพูดว่า "เชื่อมกันแล้ว"

| พูดได้ | พูดไม่ได้ |
|---|---|
| "ส่งออกได้แล้ว เห็นแถวในฐานเขา N แถว" | "เชื่อมสองระบบแล้ว" (ถ้ามีแต่ขา push) |
| "ครบครึ่งเดียว — ขา pull ยังติด X" | "ข้อมูลไหลสองทาง" |
| "เขาเห็น event ที่เราส่ง" | "เขาเห็นภาพรวมของเรา" |

🔴 **ขา push ≠ ขา pull** · เชื่อมครึ่งเดียวต้องพูดว่าครึ่งเดียว ทุกครั้ง

---

## กฎเรื่องเวลา (พลาดง่ายที่สุด และเสียหายเงียบที่สุด)

🔴 **"ยังไม่เห็น" ≠ "ไม่มี"** — ใช้กับ CI run · แถวในฐาน · log · cache ของ CDN
เคสจริง: เรียกดูรายการ CI run ไม่กี่วินาทีหลัง push ตอนที่ยังไม่ถูกสร้าง แล้วสรุปว่า
"ระบบ CI เสียทั้งรีโป" แล้วไปหยิบ error ของบริการอื่นที่ไม่เกี่ยวมายืนยัน

**กติกา**: ช่องว่างระหว่าง *ลงมือ* กับ *เรียกดู* น้อยกว่า ~2 นาที = **ตรวจไม่ได้ ไม่ใช่ไม่มี**
⇒ รอแล้วดูซ้ำ · อ่าน `created_at` เทียบกับเวลาที่ลงมือ · ห้ามขยายข้อสังเกตแคบเป็นข้อสรุปกว้าง

## เช็คลิสต์ก่อนบอกว่า "เสร็จ"

- [ ] ① ฐานที่เขียน = ฐานที่ผู้อ่านอ่าน (ยืนยันจาก config ของ endpoint + env ของแอปปลายทาง)
- [ ] ② นับแถวปลายทาง **ก่อน** ทดสอบ แล้วนับซ้ำหลังทดสอบด้วยคำสั่งเดียวกัน
- [ ] ③ ไล่ดูแถวใหม่ทีละแถวว่าตรงตารางแมป (ไม่ใช่แค่จำนวนเพิ่ม)
- [ ] ④ grep ไฟล์ที่ผู้ใช้โหลดจริง เจอค่า env ที่ควรเข้า + ชื่อไฟล์ hash เปลี่ยนจากรอบก่อน
- [ ] ⑤ ของเดิมยังอยู่ (คีย์/URL อื่นไม่หายไปจากการแก้ค่าในรอบเดียวกัน)
- [ ] ⑥ ไม่มีคีย์ในรีโป · JWT ที่ขึ้น production เป็น `anon` ของ project ที่ตั้งใจ ไม่ใช่ `service_role`
- [ ] ⑦ ทุกค่าใน taxonomy ของเขาอยู่กองใดกองหนึ่ง (แมป / ไม่แมปพร้อมเหตุผล) — มีเทสต์บังคับ
- [ ] ⑧ ด่าน consent fail-closed และเทสต์จับ **จุดเรียกใช้**
- [ ] ⑨ เห็นผล CI + deploy run ล่าสุดด้วยตาตัวเอง (ไม่ใช่เชื่อว่า push แล้วต้องรัน)
- [ ] ⑩ ประโยคที่จะพูดกับเจ้าของ ไม่มีคำว่า "เชื่อมแล้ว" เกินกว่าที่พิสูจน์ได้

## สิ่งที่ต้องเหลือไว้เป็นกลไก ไม่ใช่ความตั้งใจ

| ความผิดที่กัน | กลไก |
|---|---|
| ลืมว่าปลายทางเป็นฐานไหน | ไฟล์เดียวที่รู้ชื่อปลายทาง (config ถือแค่สวิตช์) + เทสต์บังคับ |
| แอบเรียก API/ตารางของอีกระบบจากที่อื่น | เทสต์สแกนโค้ดจริง (ตัดคอมเมนต์ก่อน) จับ **จุดเรียกใช้** |
| ฝังคีย์ | เทสต์ห้ามรูปแบบ JWT ทั้งรีโป |
| เดาหมวดให้ของที่แมปไม่ได้ | เทสต์บังคับว่าทุกค่ามีที่อยู่ |
| เผลอเปลี่ยน test → live | เทสต์ล็อกค่า flag |
| ตัวเลขในเอกสารที่ไม่มีใครเฝ้า | เลิกเขียนตัวเลขที่ยืนยันไม่ได้ หรือรันจริงก่อนอ้างทุกครั้ง |

🔴 **ที่กันด้วยโค้ดไม่ได้ ให้เขียนเป็นกฎและบอกตรง ๆ ว่าไม่มีกลไก** — อย่าแกล้งว่ามี
