# งานเสร็จเมื่อผู้ใช้ได้ใช้จริง ไม่ใช่เมื่อเขียนโค้ดเสร็จ

> **ที่มา: 17–18 ส.ค. 2569** — วันเดียวเจอบั๊ก 6 ตัวติดกัน **ทุกตัวเป็นโค้ดที่เขียนถูก**
> เทสต์ผ่าน typecheck ผ่าน build ผ่าน แต่ไม่เคยทำงานจริงต่อหน้าผู้ใช้เลย
> ตัวใหญ่สุด: `Worker` ทั้งไฟล์ไม่เคยถูกเรียกตอนคนเปิดหน้าเว็บ — ลิงก์สั้นที่ปักหมุดใน
> YouTube/TikTok/FB ไม่ redirect · SEO ฝั่ง server ไม่ทำงานเลยสักครั้ง

---

## กฎเดียวที่ต้องจำ

**เครื่องมือทุกตัวที่เราใช้ ตรวจแค่ว่า "โค้ดถูก" — ไม่มีตัวไหนตรวจว่า "โค้ดถูกเรียกใช้"**

`tsc` · `vitest` · `eslint` · `wrangler --dry-run` — ผ่านหมดได้ทั้งที่ฟีเจอร์ตายสนิท

---

## 4 ชั้นที่ต้องพิสูจน์ (แต่ละชั้นเคยพังมาแล้วจริง)

### ชั้นที่ 1 — โค้ดถูกเรียกใช้จริงไหม

**เคสจริง:** `run_worker_first` ไม่ได้ตั้ง → Cloudflare เสิร์ฟ `index.html` ก่อน **โดยไม่เรียก Worker**
ทุกอย่างใน `server.ts` (ลิงก์สั้น · SEO · sitemap) จึงเป็นโค้ดตายมาตลอด

**ตัวหลอกที่อันตราย:** `/api/*` ยัง**ทำงานปกติ** (POST ไม่ใช่ navigation request)
→ เห็นบางส่วนทำงาน เลยเชื่อว่าทั้งไฟล์ทำงาน

**ถามตัวเอง:**
- แพลตฟอร์มเรียกโค้ดนี้ *เมื่อไหร่* — เงื่อนไขอะไร ใครเป็นคนตัดสิน?
- มี default ของแพลตฟอร์มที่เปลี่ยนตาม `compatibility_date` / เวอร์ชัน / flag ไหม?
- ถ้าโค้ดนี้ถูกลบทิ้งทั้งไฟล์ **จะมีอะไรพังให้เห็นไหม?** (ถ้าไม่ = อาจไม่เคยรันอยู่แล้ว)

### ชั้นที่ 2 — ข้อมูลที่รับมา หน้าตาตรงกับที่ประกาศไหม

**เคสจริง:** migration แก้ `landing_funnel_agg` ทำคีย์ `engaged`/`bounce` หาย + เปลี่ยน
`by_ref` จากตัวเลขเป็นก้อน → หน้าแอดมินพังทั้งหน้า (React error #31) และก่อนพัง
เคยโชว์ `bounce 0` ทั้งที่ค่าจริงคือ **22 จาก 67 (33%)**

**รากปัญหา:** `data as Partial<Shape>` = การ **"ประกาศ"** ว่าข้อมูลหน้าตาแบบนี้ ไม่ใช่การ **"ตรวจ"**
TypeScript เชื่อคำประกาศเสมอ — และ `?? 0` เปลี่ยนคีย์ที่หายให้กลายเป็นเลข 0 ที่ดูเหมือนข้อมูลจริง

> ⚠️ **ผิดแบบเงียบ อันตรายกว่าจอพัง** — จอพังมีคนบอก แต่เลข 0 ปลอมถูกเอาไปตัดสินใจต่อ

**ต้องทำ:**
- เขียน `normalize()` ที่รับ `unknown` แล้วตรวจจริง — ห้ามใช้ `as Partial<>` กับข้อมูลข้ามระบบ
- **ทนได้ทั้งสคีมาเก่าและใหม่** เพราะ DB กับหน้าเว็บ **deploy คนละเวลาเสมอ**
- ค่าขยะทุกแบบ (`null` `'ข้อความ'` `42` `[]`) ต้องไม่ทำให้ throw

### ชั้นที่ 3 — เครื่องมือที่ใช้ตรวจ คือตัวเดียวกับที่ใช้จริงไหม

**เคสจริง 2 รอบ:**
- `tsc --noEmit` ที่ราก = no-op (solution tsconfig `files: []`) → รายงาน "สะอาด" หลายครั้งจากคำสั่งที่ไม่ตรวจอะไรเลย
- `npx wrangler --dry-run` บนเครื่อง = **4.123.0** (ล่าสุด) แต่ CI ตรึง **3.114.0** → dry-run ผ่าน แต่ deploy ล้มทันที

**ต้องทำ:**
- **ตรึงเวอร์ชันเครื่องมือแบบเป๊ะ** (ไม่มี `^`) และให้ CI ใช้ตัวเดียวกัน
- เขียนเทสต์บังคับว่าเวอร์ชันใน `package.json` = เวอร์ชันใน workflow
- ก่อนเชื่อผลเครื่องมือ: **ทำให้มันแดงก่อน** ถ้าทำให้แดงไม่ได้ แปลว่ามันไม่ได้ตรวจอะไร

### ชั้นที่ 4 — ของที่ deploy คือของที่เขียนไหม

**เคสจริง:** push แล้วบอกผู้ใช้ว่า "แก้แล้ว ลองทดสอบได้เลย" → **CI ล้มทั้ง run**
ผู้ใช้ทดสอบตามที่บอกแล้วยังเจอของเดิม เพราะการแก้ไม่เคยขึ้น production

> **"push แล้ว" ≠ "อยู่บน production แล้ว"**

**ต้องทำ:** เช็คสถานะ CI ให้เห็น `conclusion: success` **ก่อน**บอกผู้ใช้ว่าเสร็จ
และเปิด log ดู warning ด้วย — warning ประเภท `Unexpected fields found in ...`
แปลว่า **config ถูกตัดทิ้งเงียบ ๆ** (เจอจริง: `observability.persist` หายไปกับ wrangler v3)

## เทคนิคกลาง: Contract Test

ชั้น 1–4 ใช้ท่าเดียวกันหมด — **อย่าเชื่อ type อ่านไฟล์ต้นทางจริง**

```
เทสต์ → อ่านไฟล์จริง (migration .sql / wrangler.jsonc / workflow .yml)
      → จำลองกติกาของแพลตฟอร์ม
      → ยืนยันว่าสิ่งที่โค้ดต้องการ มีอยู่จริงในไฟล์นั้น
```

ตัวอย่างที่ใช้อยู่ในโปรเจกต์นี้:

| เทสต์ | ผูกอะไรเข้ากับอะไร |
|---|---|
| `rpcContract.test.ts` | interface TS ↔ คีย์ใน `jsonb_build_object` ของ migration ล่าสุด |
| `workerRouting.test.ts` | เส้นทางใน `server.ts` ↔ `run_worker_first` ใน `wrangler.jsonc` |
| `deployToolchain.test.ts` | เวอร์ชันเครื่องมือใน `package.json` ↔ ใน workflow ↔ ฟีเจอร์ที่ config ใช้ |

**ห้ามข้าม:** เทสต์ที่ไม่เคยเห็นมันแดง = ไม่รู้ว่ามันตรวจอะไรอยู่
ถอดการแก้ออก → ดูให้เห็นว่าล้ม → ใส่กลับ (ทำจริงทุกตัวในตารางข้างบน)

## สัญญาณเตือนว่ากำลังจะพลาด

| สัญญาณ | แปลว่า |
|---|---|
| `data as Partial<X>` / `?? 0` / `catch {}` ตรงรอยต่อระบบ | ข้อมูลผิดจะกลายเป็นค่าที่ดูปกติ |
| "ฟีเจอร์นี้เขียนครบแล้ว แต่ไม่มีใครใช้เลย" | อาจไม่เคยถูกเรียก — ไปพิสูจน์ชั้นที่ 1 |
| ตัวเลขบนแดชบอร์ดที่ "ดูดีเกินคาด" หรือ "เป็น 0 พอดี" | มักคือคีย์หาย/ตัวนับพัง ไม่ใช่ความจริง |
| แก้ config แล้ว dry-run ผ่านทันที | เช็คว่าเครื่องมือเวอร์ชันเดียวกับ CI ไหม |
| ข้อมูลจริงขัดกับสิ่งที่โค้ด "ควรจะทำ" | **นี่คือเบาะแสทอง** — เชื่อข้อมูล อย่าเชื่อโค้ด |

> **เบาะแสทองของวันนั้น:** ตาราง error บันทึก `path: /customer`
> แต่ `/customer` เป็นลิงก์สั้นที่ **ต้อง** redirect เสมอ — pathname ค้างอยู่ไม่ได้
> ข้อเท็จจริงเล็ก ๆ ข้อเดียวนี้พาไปเจอว่า Worker ไม่เคยรัน
