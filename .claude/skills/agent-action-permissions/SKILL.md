# สิทธิ์ของการกระทำของ AI Agent — ต้องบังคับได้ ไม่ใช่ขอไว้ใน prompt

> ตั้งขึ้น 20 พ.ย. 2569 จาก PDF ที่เจ้าของส่งมา: *"คู่มือสำหรับนักพัฒนา: การประมวลผลข้อมูลสตรีมมิ่งและ
> การเชื่อมต่อระบบปัญญาประดิษฐ์"* (§6 Paperclip Connectors v2026.1117.0)
> 🟢 อ่านครบทั้งฉบับ (§1–6.3)

## 0. เอกสารต้นทางเป็นสองเรื่องเย็บติดกัน — ต้องแยกให้ออก

| ภาค | เนื้อหา | ใช้กับรีโปนี้ |
|---|---|---|
| **§1–5** | API reference ของ `confluent-kafka-python` (Producer/Consumer · Schema Registry · Serdes · KIP-932 · AsyncIO · AdminClient) | 🚫 **คนละเฟสและคนละภาษา** — รีโปนี้ไม่มี Python ไม่มี Kafka · คำตัดสินอยู่ใน skill `rag-data-streaming` ข้อ 3 |
| **§6** | **Paperclip Connectors — การกำกับสิทธิ์ของ AI Agent** | ✅ **ใช้ได้ทันที และเป็นช่องว่างจริงของเรา** (ข้อ 2) |

⚠️ แต่ §5.2 มี **บทเรียนวิศวกรรมหนึ่งข้อที่ตรงกับบั๊กที่เราเพิ่งเจอเอง** — อยู่ในข้อ 4 ห้ามข้าม

## 1. 🔴 หลักการเดียวที่ทั้ง skill นี้ยืนอยู่บน

**สิทธิ์ที่เขียนไว้ใน prompt ไม่ใช่สิทธิ์ — มันคือคำขอ**

เอกสารพูดเรื่องนี้ตรง ๆ และเป็นข้อสังเกตที่คมที่สุดในทั้งฉบับ:

> *"การกำหนดสิทธิ์แบบเครื่องมือรายชิ้น (Per-tool Ask-first controls) บน Connector นี้
> จะมีผลควบคุมเฉพาะการสั่งงานผ่าน Connector Interface เท่านั้น
> **ไม่ได้มีผลครอบคลุมไปถึงการสั่งงานตรงผ่าน Shell, Git หรือ gh CLI ในเครื่อง Local**"*

⇒ สิทธิ์ผูกกับ **ทางที่คำสั่งเดินผ่าน** ไม่ใช่ผูกกับ "ความตั้งใจของเอเจนต์"
⇒ มีช่องทางไหนที่ไม่ผ่านด่าน ด่านนั้นก็เป็นแค่การตกแต่ง

## 2. 🔴 ช่องว่างจริงของเรา (ตรวจสดในโค้ด 20 พ.ย. 2569)

| สิ่งที่เอกสารกำหนด | ของเราวันนี้ | สถานะ |
|---|---|---|
| ระดับสิทธิ์ต่อเครื่องมือ 3 ชั้น `Allowed` / `Ask first` / `Off` | `grep` หา `askFirst`/`'allowed'`/`requireApproval` ทั่ว `src/` = **0 แห่ง** | 🔴 **ไม่มี** |
| สิทธิ์ขั้นต่ำเท่าที่จำเป็น (Least Privilege) ต่อเอเจนต์ | `Agent.mandate` = **ข้อความอิสระ** (`src/types.ts`) ไม่มีใครบังคับใช้ | 🔴 เป็นคำอธิบาย ไม่ใช่สิทธิ์ |
| แยกบัญชี/ขอบเขตตามบทบาทเอเจนต์ | เอเจนต์ทุกตัวใช้ทางออกชุดเดียวกัน | 🔴 ไม่มีการแยก |
| คิวรออนุมัติจากมนุษย์ | `resources.applyApproval()` (เฉพาะทรัพยากร) · `boardRoom.AGENDA` (วาระบอร์ด) | 🟡 **มีแต่เฉพาะกิจ** ไม่ใช่กลไกกลาง |
| ขอบเขตของเอเจนต์ | `AI_GUARDRAILS` ข้อ 6 สั่งโมเดลว่า *"ห้ามพยายามเข้าถึงข้อมูลผู้ใช้/บริษัทอื่น"* | 🔴 **อยู่ใน prompt ⇒ เป็นคำขอ ไม่ใช่ด่าน** |
| จำกัดปลายทางที่เอเจนต์ติดต่อได้ | `egressGuard.ALLOWED_HOSTS` = 2 โฮสต์ · `guardedFetch` โยน error ถ้าไม่อยู่ในรายชื่อ | 🟢 **นี่คือด่านจริงตัวเดียวที่เรามี** |

🟢 **ข่าวดี**: `egressGuard` พิสูจน์ว่าเราทำแบบ "บังคับได้" เป็นแล้ว — มันคือ Least Privilege ของ **ขาออก**
🔴 **ข่าวร้าย**: เรายังไม่มีของแบบเดียวกันสำหรับ **การกระทำ** (ส่งอีเมล · โพสต์ · เปิด PR · จ่ายเงิน · แก้ข้อมูลผู้ใช้)

## 3. ✅ กติกาบังคับก่อนให้เอเจนต์ "ลงมือทำ" อะไรใหม่

ก่อนเพิ่มความสามารถให้เอเจนต์ ต้องตอบครบ 4 ข้อ — ตอบไม่ได้ = **ยังไม่สร้าง**

1. **การกระทำนี้อยู่ชั้นไหน** — `Allowed` (ย้อนกลับได้ + ไม่เห็นจากข้างนอก) · `Ask first` (ออกไปข้างนอก หรือใช้เงิน) · `Off` (ยังไม่ถึงเวลา)
   🔴 **ค่าเริ่มต้นคือ `Ask first`** — ไม่ใช่ `Allowed` · ของที่ย้อนไม่ได้ขึ้น `Off` จนมีคนสั่งเปิด
2. **ด่านอยู่บนทางที่คำสั่งเดินจริงไหม** — ถ้าเลี่ยงด่านได้ด้วยการเรียกตรง ด่านนั้นไม่นับ (ข้อ 1)
3. **ทำแล้วเหลือร่องรอยไหม** — ใครสั่ง · เมื่อไร · ใครอนุมัติ · ผลเป็นอะไร
   เอกสารเรียกชั้นนี้ว่า Review queue · ของเราคือ `boardRoom` + `client_errors`
4. **คนปฏิเสธได้จริงไหม** — "คิวอนุมัติ" ที่กดปฏิเสธแล้วงานเดินต่อ = ไม่ใช่คิวอนุมัติ

🔴 **เส้นที่ห้ามข้ามของรีโปนี้** (มาจากกฎที่ freeze ไว้แล้ว ไม่ใช่กฎใหม่):
   · การใช้เงิน/ขยายงบ → ผ่าน `founderMindset` 6 ด่าน + `decisionRules` `paid-scale` ก่อน
   · แตะ schema → `releaseGates.schemaChangeAllowed()` ยังกั้น
   · เขียนตาราง `marketing_*` ของทั้งสอง project → `ownershipBoundary.test.ts` ห้ามอยู่
   · ปลายทางขาออกใหม่ → ต้องเพิ่มใน `egressGuard.ALLOWED_HOSTS` = **การตัดสินใจเรื่องความปลอดภัย = งานเจ้าของ**

## 4. ⚠️ บทเรียนจาก §5.2 ที่ตรงกับบั๊กที่เราเพิ่งเสียเวลาไปกับมันเอง

เอกสารเตือนว่าให้ใช้ `incremental_alter_configs()` แทน `alter_configs()` เพราะ

> *"`alter_configs()` มีพฤติกรรมสุ่มเสี่ยงในการ**ย้อนค่าคอนฟิกที่ไม่ถูกระบุในคำสั่งกลับไปเป็นค่า Default ทั้งหมด**"*

🔴 **นี่คือบั๊กตัวเดียวกับ ledger #82 ของเรา คนละระบบ**: `wrangler` ลบ `vars` ทั้งหมดก่อน deploy
⇒ `ANTHROPIC_API_KEY` ที่ประกาศเป็นค่าว่างใน `wrangler.jsonc` ถูกล้างทุกครั้งที่ merge
⇒ กล่อง "ลอง AI" พังอยู่บน production โดยไม่มีใครรู้

**กฎที่ได้**: เครื่องมือตั้งค่าใด ๆ ต้องถามก่อนใช้ว่า **"คำสั่งนี้แทนทั้งชุด หรือแก้เฉพาะคีย์ที่ระบุ"**
แบบ *แทนทั้งชุด* จะลบของที่เราไม่ได้พูดถึง — และของที่ถูกลบมักเป็น secret ที่ตั้งด้วยมือ

## 5. 🪣 ของจาก §1–5 ที่ "หลักการ" ใช้ได้ แม้โค้ดใช้ไม่ได้

| แนวคิดในเอกสาร | ของเราที่ทำเรื่องเดียวกันอยู่แล้ว |
|---|---|
| Exactly-Once / กันประมวลผลซ้ำ | `appliedPaymentIds` · `payment_submissions.trans_ref` unique · `sub.reminderSentFor` · `reportedMissing` ใน `aiFailure.ts` |
| **Poison record → `REJECT` ไม่ล้มทั้ง batch** | `ai-plan.extractJson()` + `balanceClose()` กู้ JSON ที่ถูกตัด แทนการโยนทิ้งทั้งคำตอบ |
| `RELEASE` เมื่อเป็น transient error | `quota.ts` **fail-open** ทุกจุด: บั๊กตัวนับต้องไม่ทำให้ AI ล่ม |
| Context manager บังคับ `close()` | ส่วนที่เรายังหลวม — ดูเทียบกับ `ResizeObserver`/listener ที่ต้องถอนใน `useEffect` |
| Data Contracts + ตรวจความเข้ากันได้ของ schema | `rpcContract.test.ts` (SQL↔TS) · `workerRouting.test.ts` · `deployToolchain.test.ts` |
| CSFLE เข้ารหัสรายฟิลด์ | หลักเดียวกับกฎ PDPA ของเรา: `quickcheck_submissions` **ไม่เก็บข้อความอิสระ** · `client_errors` ไม่เก็บ IP/user id |

🔴 **ห้ามใช้ตารางนี้เป็นเหตุผลให้เอา Kafka เข้ามา** — มันบอกว่า *"ปัญหาเหล่านี้เรารู้จักและแก้ด้วยของที่เรามี"*
ไม่ใช่ *"เราควรใช้เครื่องมือเดียวกับเขา"* (เหตุผลเต็มอยู่ใน `rag-data-streaming` ข้อ 3)

- **`confluent-kafka-python` ทั้งภาค** — ไม่มี Python ในรีโปนี้
