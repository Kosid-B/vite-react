# Dynamic PLG — กฎบังคับของโปรเจกต์

> ยืนยันโดยเจ้าของ 16 ส.ค. 2569: *"การแก้ไขและพัฒนาระบบ กฎคือต้องเป็น PLG และเป็น Dynamic PLG ตามผู้ใช้งาน รวมถึง Landing Page ต้องเป็น Dynamic ตามผู้ใช้"*

## สองชั้นที่ต้องผ่านทั้งคู่

**ชั้น 1 — PLG:** ผู้ใช้ต้องได้คุณค่าจริงด้วยตัวเอง โดยไม่ต้องรอเรา
ไม่มีคนกลางเป็นประตู · ไม่ต้องนัดเดโม · ไม่ต้องรออนุมัติ · ไม่ต้องคุยกับเซลส์ก่อนเห็นค่า

**ชั้น 2 — Dynamic:** สิ่งที่เขาเห็นต้องเปลี่ยนตาม "สิ่งที่เรารู้เกี่ยวกับเขาแล้ว"
ถ้าระบบรู้อะไรบางอย่างเกี่ยวกับคนคนนี้ แล้วยังแสดงผลเหมือนคนที่เราไม่รู้อะไรเลย = ผิดกฎ

## คำถาม 3 ข้อ ก่อนส่งงานทุกชิ้น

1. **เขาได้คุณค่าเองได้ไหม โดยไม่ต้องมีเราอยู่ด้วย?** ถ้าไม่ = ยังไม่ใช่ PLG
2. **ตอนนี้ระบบรู้อะไรเกี่ยวกับเขาบ้าง?** (มาจากไหน · เคยกรอกอะไร · อยู่ขั้นไหน · แพ็กอะไร · กลับมาครั้งที่เท่าไร)
3. **สิ่งที่เขาเห็น เปลี่ยนตามข้อ 2 หรือยัง?** ถ้าไม่เปลี่ยน = ทิ้งบริบทฟรี ๆ

## สัญญาณที่รู้อยู่แล้ว และต้องเอามาใช้

| สัญญาณ | มาจาก | ต้องเปลี่ยนอะไร |
|---|---|---|
| มาจากบทความไหน | CTA ติด `?seg=` + `?from=` (`lib/ctaContext.ts`) | พาดหัวหน้าปลายทาง |
| แคมเปญ/แพลตฟอร์ม | `?s=fb` · utm · referrer | ข้อความ + การวัดผล |
| เป้าหมายที่เลือกตอนเข้า | `AppData.onboardGoal` | เมนู (focus mode) + หน้าแรกที่พาไป |
| เคยกรอกตรวจสินค้าเร็ว | `readQuickDraft()` | ทักกลับด้วยตัวเลขของเขา ไม่ใช่เริ่มใหม่ |
| แพ็ก/สถานะทดลอง | `access.ts` | สิ่งที่ปลดล็อก + สิ่งที่ชวนอัปเกรด |
| ความคืบหน้า Roadmap | `trialRoadmap.nextStep()` | ขั้นถัดไปที่ควรทำ |

## ⚠️ กับดักที่เคยพลาดจริง — "ส่งไปแล้วปลายทางไม่ใช้"

16 ส.ค. 2569: CTA ท้ายบทความส่งคนไป `/start` โดยไม่พก seg
และตอนแก้รอบแรก ผมเติม seg ให้ CTA แล้ว **แต่ `/start` ไม่ได้อ่าน `?seg=` เลย** — ถ้าไม่ตรวจปลายทางก็จะประกาศว่าแก้เสร็จทั้งที่ไม่มีอะไรเปลี่ยน

**กฎที่ได้มา: ต้องตรวจทั้งสาย ไม่ใช่ปลายเดียว**
`ต้นทาง (ส่งบริบท) → ทาง (บริบทไม่ตกหล่น) → ปลายทาง (ใช้บริบทจริง)`

กลไกที่บังคับไว้แล้ว: `src/lib/__tests__/dynamicPlg.test.ts`
— ทุก seg ที่ CTA ส่งไป ต้องมีพาดหัวของ seg นั้นที่ปลายทางจริง ไม่งั้นเทสต์ล้ม

## เส้นแบ่งที่ห้ามข้าม

Dynamic **ไม่ใช่** ใบอนุญาตให้หลอก — ยังอยู่ใต้กฎเดิมทุกข้อ:

- ❌ ห้ามแต่งตัวเลขให้ดูตรงกลุ่ม (`landingClaims.test.ts` + `dynamicPlg.test.ts` สแกนอยู่)
- ❌ ห้าม scarcity ปลอม / นับถอยหลังปลอม / "เหลือ 3 ที่" ที่ไม่จริง
- ❌ ห้ามซ่อนราคาจากบางกลุ่มเพื่อให้ต้องทัก — ขัด PLG ตรง ๆ
- ❌ ห้ามเก็บข้อมูลเกินที่จำเป็นเพื่อทำ personalization (PDPA · ดู `quickcheck_submissions` ที่จงใจไม่เก็บชื่อสินค้า)
- ✅ ต้องมี variant ตั้งต้นที่ปลอดภัยเสมอ — ไม่รู้จักเขา = แสดงเวอร์ชันกลางที่ตรวจแล้ว ไม่ใช่เดา

- [ ] ตรวจแล้วว่า **ปลายทางใช้สัญญาณนั้นจริง** ไม่ใช่แค่ส่งไป

- [ ] ไม่มีตัวเลข/คำสัญญาที่พิสูจน์ไม่ได้ในทุก variant
- [ ] มีเทสต์ผูกต้นทาง–ปลายทางไว้ (พิสูจน์แล้วว่าล้มจริงเมื่อสายขาด)
