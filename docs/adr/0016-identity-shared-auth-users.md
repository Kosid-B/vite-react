# ADR-0016 — identity: แมปบัญชีเดียวเข้า `auth.users` ของเรา แล้วให้ Postgres บังคับเส้นแบ่ง

- **สถานะ**: `accepted`
- **วันที่**: 26 พ.ย. 2569
- **ผู้ตัดสิน**: เจ้าของ (*"ข"*) — เปลี่ยนจาก (ก) หลังเห็นตัวเลขจริง
- **แทน**: [ADR-0015](0015-identity-service-key-scoped.md) (`superseded`)

## บริบท

ADR-0015 บันทึกว่าเจ้าของเลือกทาง **(ก)** service key แบบจำกัดขอบ · การตัดสินนั้นยืนอยู่บนความเข้าใจว่า
*"ผู้ใช้ของแอป OS มี 11 คน"* ซึ่งทำให้ทาง **(ข)** ดูแพง (ต้องย้าย 11 บัญชี · 11 คนตั้งรหัสใหม่)

🔴 **ตัวเลขนั้นอ่านผิด** (ledger #109) — วัดสดยืนยันสองฝั่ง 26 พ.ย. 2569:

| วัด | ค่า |
|---|---|
| `marketing_os.workspace_members` ทั้งหมด | 11 |
| ในนั้นเป็น fixture ของเทสต์ RLS (`RLS_TEST_WORKSPACE_A`/`B` · สร้างวินาทีเดียวกัน · ข้อมูลว่าง) | **10** |
| 🟢 **ผู้ใช้จริง** (owner ของ `ceo-ai-thailand` `e82e7d93…`) | **1** |
| อีเมลของคนนั้น (อ่านจาก `auth.users` ของ project เขา) | `support@b-tctraining.com` |
| 🟢 บัญชีอีเมลเดียวกันใน `auth.users` **ของเรา** | **มีอยู่แล้ว** `d9c45d9c…` (สร้าง 27 มิ.ย. 2569) |

⇒ ต้นทุนจริงของ (ข) = **แมป 1 แถว** ไม่ใช่ย้าย 11 บัญชี · ไม่ต้องสร้างบัญชีใหม่แม้แต่บัญชีเดียว
⇒ เหตุผลเดียวที่เคยทำให้ปัดตก (ข) หายไปทั้งหมด ⇒ เจ้าของเปลี่ยนเป็น (ข)

## การตัดสินใจ

**migration `0072_marketing_os_member_rls`** — ให้ **Postgres** บังคับเส้นแบ่ง workspace ไม่ใช่โค้ดแอป

1. แมปสมาชิก: `(e82e7d93…, d9c45d9c…, 'owner')` ด้วย `on conflict do nothing`
   ⚠️ **ไม่ลบแถวของผู้ใช้เดิมของเขา** — เก็บไว้เป็นร่องรอยว่าข้อมูลมาจากไหน
2. `marketing_os.is_workspace_member(uuid)` เป็น `security definer`
   (ไม่งั้น policy ของ `workspace_members` จะเรียกตัวเองวนซ้ำ)
3. `grant usage on schema marketing_os to authenticated` + grant **ระบุชื่อตารางทีละตัว 17 ตัว**
4. RLS policy อิงการเป็นสมาชิกบนทั้ง 17 ตาราง
5. 🔴 **`workspaces` + `workspace_members` ให้ `select` เท่านั้น** —
   ถ้าให้ `insert` บน `workspace_members` ได้ สมาชิกจะเพิ่มคนอื่นเข้า workspace ตัวเองได้
   ซึ่งแอป single-tenant ไม่ต้องใช้ ⇒ ปิด
6. 🔴 **อีก 6 ตารางยังเป็น `service_role` เท่านั้น**
   `marketing_behavior_*` ×4 (ท่อ ingest ของเรา) · `marketing_brand_rules` · `workspace_state`
   ⇒ เปิดเท่าที่แอป query จริง ไม่เปิดเผื่อ
7. 🔴 **`anon` ไม่ได้รับอะไรเลย** — ไม่มี usage · ไม่มี grant · ไม่มี policy

## กลไก

| กลไก | กันอะไร |
|---|---|
| **ทดสอบ RLS ด้วยการสวมบทผู้ใช้จริงใน SQL** (`set local role authenticated` + `request.jwt.claims.sub`) — ไม่ใช่แค่ดูว่า policy มีอยู่ | กัน "เขียน policy แล้วคิดว่าทำงาน" ซึ่งเป็นความผิดที่พบบ่อยที่สุดของ RLS |
| `ownershipBoundary.test.ts` — กฎ B1 เขียนใหม่ให้ **แคบลง 2 แกน**: ① `anon` ห้ามตลอดกาล ไม่มีข้อยกเว้น ② `authenticated` ได้เฉพาะเมื่อ migration เดียวกันมี `create policy` ③ ห้าม `all tables in schema` และห้าม `alter default privileges` | กันการเปิดสิทธิ์เปล่าที่ไม่มี policy คุม และกันตารางที่สร้างทีหลังได้สิทธิ์ติดมาเงียบ ๆ (บทเรียน 0069) |
| เทสต์สังเคราะห์ 8 เคส | พิสูจน์ว่าด่านยัง **จับของผิด** ได้ทุกแบบ และ **ไม่จับของที่ถูก** — ไม่ใช่ด่านที่ผ่อนให้ 0072 ผ่าน |
| เทสต์อ่าน `0072` ตัวจริง: ห้ามมี `to anon` · ห้าม `all tables in schema` · ห้าม `alter default privileges` · 4 ตารางที่ไม่ควรเปิดต้องไม่ถูกเปิด · `workspace_members` ต้องเป็น `select` เท่านั้น | กันการแก้ไฟล์ภายหลังให้กว้างขึ้นโดยไม่มีใครเห็น |
| `IDENTITY_IMPLEMENTED = true` แยกจาก `APP_REPOINTED = false` | identity จบแล้ว **แต่ข้อ ① ยังไม่จบ** ⇒ `osRepointReady()` ยังเป็น `false` · เทสต์บังคับว่าถอย identity กลับ = blocker 2 ข้อ ไม่ใช่ 1 |

## ผลที่ตามมา

- 🟢 **เส้นแบ่ง workspace บังคับโดยฐาน** — พลาดในโค้ดแอปก็ยังรั่วไม่ได้ (นี่คือข้อที่ (ก) ให้ไม่ได้)
- 🟢 **ล็อกอินจบในตัว** — เจ้าของใช้บัญชีเดิมที่มีอยู่แล้ว ไม่ต้องตั้งรหัสใหม่ ไม่ต้องสร้างบัญชี
- 🟢 **ไม่ต้องมี service key ในแอป** ⇒ ไม่มีกุญแจผีให้หลุด
- 🟢 ย้อนกลับได้: `drop policy` + `revoke … from authenticated` + ลบแถวสมาชิกที่เพิ่ม = กลับสภาพเดิม
- 🔴 **ลูกค้าของเรา 3 บัญชีที่เหลือมี `authenticated` เหมือนกัน** — ปลอดภัยเพราะ policy อิงการเป็นสมาชิก
  (วัดแล้ว = 0 แถว) **แต่กฎนี้ยืนอยู่บน policy ไม่ใช่บน grant** ⇒ ลบ policy = เปิดหมดทันที
  ⇒ นี่คือเหตุผลที่ด่าน B1 บังคับว่า grant กับ policy ต้องมาคู่กันเสมอ
- 🔴 **ด่านสุดท้ายที่เหลือ: แอป OS ยังชี้ไป `bjozpwdtqbpwcxnqguka`** — ต้องแก้ 3 ค่า
  (`NEXT_PUBLIC_SUPABASE_URL` · anon key · `db: { schema: 'marketing_os' }`)
  ⇒ อยู่บนเครื่องเจ้าของ · เซสชันคลาวด์เปิดโฟลเดอร์ไม่ได้
- ⚠️ **ถ้าวันหน้ามีผู้ใช้จริงหลายคนหลาย workspace** ให้ทบทวนข้อ 5 ใหม่ (วันนี้ปิดการเพิ่มสมาชิกไว้)
- ⚠️ fixture `RLS_TEST_WORKSPACE_A`/`B` ยังอยู่ในฐานเรา · ไม่มีใครเห็นมันผ่าน policy
  (ไม่มีสมาชิกคนไหนเป็นผู้ใช้จริง) ⇒ ไม่เป็นอันตราย แต่เป็นขยะที่ทำให้อ่านตัวเลขผิดมา 11 วัน
  ⇒ **ลบได้ แต่ยังไม่ลบ** เพราะเป็นข้อมูลที่คัดลอกมา ต้องให้เจ้าของสั่ง

## ทางเลือกที่ไม่เลือก

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| **(ก) service key + ประตูเดียว** (ADR-0015) | เส้นแบ่งอยู่ในโค้ดแอป ⇒ พลาดจุดเดียวเห็นทุก workspace · เทสต์ที่บังคับต้องไปอยู่ในอีก repo ที่เซสชันคลาวด์เข้าไม่ถึง ⇒ **พึ่งวินัยคน ไม่ใช่กลไก** · และไม่แก้เรื่องล็อกอิน |
| สร้างบัญชีใหม่ในฐานเราแทนการใช้บัญชีเดิม | อีเมลเดียวกันมีอยู่แล้ว ⇒ สร้างใหม่ = มีสองบัญชีอีเมลเดียวกัน สับสนภายหลัง |
| เปลี่ยน `user_id` ของแถวเดิมให้เป็น uuid ของเรา | ลบร่องรอยว่าข้อมูลมาจากไหน · insert แถวใหม่ให้ทั้งสองอยู่ร่วมกันได้ (PK คือคู่ `workspace_id,user_id`) |
| เปิด `authenticated` ทั้ง schema แล้วค่อยเขียน policy ทีหลัง | ช่วงที่ยังไม่มี policy = เปิดหมด · และ `alter default privileges` จะทำให้ตารางอนาคตได้สิทธิ์เงียบ ๆ (บทเรียน 0069) |
| เปิดให้ `anon` ด้วยเพื่อให้หน้า public อ่านได้ | ไม่มีความต้องการนั้น และ `anon` = ใครก็ได้บนอินเทอร์เน็ต ⇒ ห้ามตลอดกาล |
