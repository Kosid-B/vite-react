# ADR-0017 — ชื่อไฟล์ migration เป็น timestamp UTC ไม่ใช่เลขลำดับ

- **สถานะ**: `accepted`
- **วันที่**: 26 พ.ย. 2569
- **ผู้ตัดสิน**: ผู้ช่วย (กติกาในรีโป · กลับคืนได้ด้วยการลบเทสต์ 1 ไฟล์) — **ครึ่งที่เป็นข้อตกลงระหว่างคน ยังรอเจ้าของ** (ดู §ผลที่ตามมา)

## บริบท

26 พ.ย. 2569 **วันเดียว** มีสองเซสชัน Claude Code เขียน production `waigsnxhrlwtiotspaim`
พร้อมกัน (เซสชันคลาวด์ = ผม · เซสชันบนเครื่องเจ้าของ) และพลาดเรื่องเดียวกัน **3 ครั้ง**:

| ledger | เกิดอะไร |
|---|---|
| #108 | migration `0070` ถูก apply โดยไม่มีไฟล์ในรีโป ⇒ ไม่มีใครอ่านโค้ดที่เปลี่ยนฐานได้ |
| #110 | เลขชน **2 คู่** (`0071` · `0072`) + สร้าง rpc `0073` ที่ไม่มีใครเรียกได้ |
| #111 | เลขชนคู่ที่ 3 (`0075`) **และทำงานซ้ำทั้งก้อน** ห่างกัน 15 นาที (09:30:11 vs 09:43:33) |

**ค่าตั้งต้นที่วัดสดบน production** (26 พ.ย. 2569 · นับจาก `supabase_migrations.schema_migrations`):

```sql
select substring(name from '^[0-9]{4}') as num, count(*)
from supabase_migrations.schema_migrations
where name ~ '^[0-9]{4}_' group by 1 having count(*) > 1;
```

⇒ **เลขที่ชนกัน 3 เลข · migration ที่เกี่ยวข้อง 6 ตัว** · ในรีโปเลขไม่ซ้ำ (77 ไฟล์ `0001`–`0077`)
แต่ **ชื่อในรีโปกับชื่อใน production ไม่ตรงกัน 3 คู่** ⇒ อ้างเลขในแชตแล้วคนละตัวกัน

🔑 **สาเหตุราก (1 ข้อ)**: *"ตัวจัดเลข" กับ "ตัวบันทึก" อยู่คนละที่* —
เลขถูก **จองตอน apply** (ฐานข้อมูล) แต่ถูก **บันทึกตอน commit** (รีโป)
และทั้งสองเซสชันตั้งเลขถัดไปโดย **นับจากรายการไฟล์ในรีโป** ซึ่งเก่าทันทีที่อีกฝ่าย apply แล้วยังไม่ commit
⇒ ไม่มีช่วงไหนที่ใครล็อกเลขได้ ⇒ **ไม่ใช่ความเลินเล่อ เป็นโครงสร้างที่ชนเองได้**

## การตัดสินใจ

**เลิกมี "เลขถัดไป" — migration ใหม่ตั้งชื่อด้วย timestamp UTC ตอนสร้างไฟล์**

```
supabase/migrations/<YYYYMMDDHHMMSS>_<ชื่อ_พิมพ์เล็ก>.sql     ← ของใหม่
supabase/migrations/0001_… – 0077_…                            ← ของเก่า ไม่แตะ
```

- รูปแบบเดียวกับที่ **Supabase ใช้เองใน `schema_migrations.version`** ⇒ ไม่ได้คิดกติกาใหม่
- เวลาที่ส่งเข้า `apply_migration` ใช้ **ชื่อเดียวกับไฟล์** ⇒ `name` ใน production = ชื่อไฟล์ในรีโป
  ⇒ เทียบสองฝั่งได้ด้วยการอ่านชื่อ ไม่ต้องจำว่าเลขไหนตรงกับเลขไหน
- ไม่ต้องขอความร่วมมือจากใคร: **สองเซสชันที่ต่างกัน 1 วินาทีก็ชนกันไม่ได้แล้ว**

⚠️ **ของเก่า 0001–0077 ไม่เปลี่ยนชื่อย้อนหลัง** — การอ้างอิงชื่อไฟล์ตรง ๆ มีอยู่ในเทสต์
(`ownershipBoundary.test.ts` อ่าน `0072` และ `0075` ด้วยชื่อ) และในเอกสารหลายที่
⇒ เปลี่ยนย้อนหลัง = ทุบของที่ทำงานอยู่ โดยไม่ได้กันอะไรเพิ่ม (ของที่ชนแล้วก็ชนไปแล้ว)

| เคสที่จำลองเหตุการณ์จริง 09:30:11 vs 09:43:33 | บันทึกว่าทำไมกติกานี้มีอยู่ — อ่านเทสต์แล้วรู้เหตุ |

**ยืนยันแดงจริง**: สร้าง `supabase/migrations/0078_probe_old_style.sql` (ไฟล์เปล่า)
⇒ แดง 2 เทสต์ พร้อมข้อความ `0078_probe_old_style.sql: ตั้งเลขลำดับ 4 หลักหลังเปลี่ยนกติกา`
⇒ ลบไฟล์ ⇒ เขียวครบ 14 เทสต์

🔴 **สิ่งที่กลไกนี้ทำไม่ได้ และต้องพูดให้ชัด**: มันอ่าน **รีโป** ไม่ได้อ่าน production
⇒ ถ้ามีใคร apply โดยไม่ commit ไฟล์ (ความผิด #108) **ด่านนี้ไม่เห็น**
กฎ #108 (*"ห้ามแก้ฐานโดยไม่มีไฟล์คู่กัน"*) จึงยังต้องอยู่ และยังเป็นข้อตกลง ไม่ใช่เทสต์

## ผลที่ตามมา

- 🟢 **เลขชนกันไม่ได้อีกโดยโครงสร้าง** — ไม่ต้องเชื่อใจใคร ไม่ต้องจำ ไม่ต้องถาม
- 🟢 ชื่อไฟล์ในรีโป = `name` ใน production ⇒ เทียบสองฝั่งได้โดยไม่ต้องมีตารางแปลง
- 🟡 ชื่อไฟล์ยาวขึ้นและเรียงด้วยสายตาได้น้อยลงกว่า `0075` — ยอมรับแล้ว (เครื่องมือเรียงให้อยู่แล้ว)
- 🔴 **ไม่ได้ปิดความผิด #111 ครึ่งที่แพงที่สุด: "ทำงานซ้ำทั้งก้อน"**
  เลขไม่ชนแล้ว แต่สองเซสชันยังลงมือเรื่องเดียวกันพร้อมกันได้เหมือนเดิม
  ⇒ ทางปิดคือ **ข้อตกลงว่าช่วงนี้ใครเป็นคนแก้ฐาน** ซึ่งเป็นการตัดสินของเจ้าของ ไม่ใช่เทสต์
  ⇒ **ห้ามอ้างว่า ADR นี้ปิดราก #108/#110/#111 ครบ** — ปิดได้เฉพาะส่วน "เลขชน"
- 🟡 สิ่งที่ผมทำได้เองระหว่างรอ และจะทำตั้งแต่วันนี้: **ก่อนตั้งชื่อ migration ทุกครั้ง อ่าน
  `supabase_migrations.schema_migrations` ของ production ก่อน** และ **บอกในแชตก่อน apply ทุกครั้ง**
