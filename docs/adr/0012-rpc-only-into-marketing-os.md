# ADR-0012 — เข้า `marketing_os` ผ่าน rpc ใน `public` เท่านั้น ห้ามพึ่ง "Exposed schemas"

- **สถานะ**: `accepted`
- **วันที่**: 26 พ.ย. 2569
- **ผู้ตัดสิน**: เจ้าของ (*"ลุยข้อ A ก่อน"* — เลือกจากตารางทางเลือก 4 ข้อ)

## บริบท

ADR-0011 ย้ายข้อมูล Marketing OS มาอยู่ schema `marketing_os` ในฐานเดียวกับผลิตภัณฑ์ และเขียนไว้เองว่า
**"ครึ่ง HTTP ยังตรวจไม่ได้จากเซสชันนี้"** (egress proxy ปฏิเสธโฮสต์ Supabase ของเรา)

🟢 **26 พ.ย. 2569 — ครึ่งนั้นถูกพิสูจน์โดยผู้ใช้จริง ไม่ใช่โดยเรา**: นับแถวแล้วพบ batch `mode:'live'`
**2 ก้อนจากหน้าเว็บจริง** (23 พ.ย. 03:52 · 25 พ.ย. 02:19 UTC) ⇒ edge function รับ HTTP ได้ ·
rpc เขียนลง `marketing_os` ได้ · trigger กาง event ออกมาครบ (events 5 → 8)

🔴 **แต่ทั้ง 2 ก้อนมี `archived_at = NULL`** — ขณะที่ 4 ก้อนที่มีค่าเป็น **แถวที่คัดลอกมาจากฐานเขา**
(archive สำเร็จบน project เดิม) ⇒ **ทุก batch ที่ผ่าน deployment ของเราล้มเหมือนกันหมด 2/2**

ไล่ทีละขั้นด้วย SQL:

| ขั้น | ผล | หลักฐาน |
|---|---|---|
| rpc เขียน batch + event | ✅ | 6 batch · 8 event ในตาราง |
| สร้าง bucket ส่วนตัว | ✅ | `marketing-behavior-private` (`public=false`) |
| อัปไฟล์เข้าคลัง | ✅ | `storage.objects` = **2** ตรงกับ 2 batch พอดี |
| อัปเดต `archived_at` | ❌ | ขั้นเดียวที่เหลือ = `db.schema('marketing_os').from(...).update(...)` |

🟡 **สาเหตุที่อนุมานได้ แต่ยืนยันตรง ๆ ไม่ได้**: PostgREST รับเฉพาะ schema ที่อยู่ใน
**"Exposed schemas"** (ค่าเริ่มต้น `public, graphql_public`) ⇒ `PGRST106`
🔴 **ทำไมยืนยันไม่ได้**: ค่านี้เป็น **config ของแพลตฟอร์ม ไม่ได้อยู่ในฐานข้อมูล** — SQL อ่านไม่เห็น
และยิง HTTP ทดสอบจากเซสชันคลาวด์ไม่ได้
🟢 **ตัดสาเหตุคู่แข่งออกได้**: `hash` ที่ใช้ `.eq()` เป็นตัวแปรเดียวกับที่ส่งให้ rpc เก็บ
⇒ "อัปเดตแล้วไม่เจอแถว" เป็นไปไม่ได้ทางตรรกะ

🟢 **และยังมีสาเหตุที่สอง ซึ่งวัดตรงได้ (พบหลังตัดสินใจแล้ว — บันทึกไว้เพราะมันทำให้คำตอบแน่นขึ้น)**:
`service_role` มี **grant บนตารางใน `marketing_os` = 0** (`information_schema.role_table_grants`)
⇒ ต่อให้เปิด Exposed schemas ก็ยังเขียนไม่ได้อยู่ดี · `rolbypassrls = true` ข้ามได้แค่ **RLS**
ไม่ได้ให้ **สิทธิ์บนตาราง** · ที่ rpc ทำงานได้เพราะเป็น `security definer` (รันในสิทธิ์เจ้าของฟังก์ชัน)
**ไม่ใช่เพราะ `service_role` มีสิทธิ์** ⇒ บั๊กนี้มีสองชั้น และทางเลือก "เปิด Exposed schemas"
ก็ **แก้ไม่หายอยู่ดี** — ซึ่งยืนยันว่าเลือกทาง rpc ถูกแล้ว

## การตัดสินใจ

**ท่อเข้า `marketing_os` ต้องผ่าน rpc ใน `public` เท่านั้น — ห้ามแตะตารางตรงจากโค้ดใด ๆ**

1. เพิ่ม `public.mark_marketing_behavior_archived(uuid, text)` (migration 0068)
   `security definer` · `search_path = ''` · `revoke` จาก `public`/`anon`/`authenticated` ·
   `grant execute` ให้ `service_role` เท่านั้น — เกณฑ์ความปลอดภัยชุดเดียวกับ 0067
2. edge function เรียก rpc แทน `.schema(...).from(...).update(...)`
3. rpc คืนค่าเป็นข้อความ **แยก 3 สถานะ**: `archived` · `already_archived` (ลองซ้ำ = ปกติ) ·
   `not_found` (ผิดจริง) ⇒ ฟังก์ชันตอบ `archive_unconfirmed` เมื่อเจอกรณีที่สาม
   — เดิมถ้าอัปเดตไม่โดนแถว จะ **เงียบสนิทแล้วตอบ 200**

🔴 **หลักการที่อยู่เบื้องหลัง ใหญ่กว่าบั๊กนี้**: *ของที่ทำงานถูกหรือผิดขึ้นกับค่าที่อยู่นอกรีโป
และเราอ่านไม่ได้ = ของที่พังเงียบแล้วไม่มีใครรู้ว่าทำไม* · `Exposed schemas` เป็นค่าแบบนั้นพอดี
(เทสต์บังคับไม่ได้ · PR review มองไม่เห็น · ไม่มี log บอก)

## กลไก

| กลไก | กันอะไร |
|---|---|
| `ownershipBoundary.test.ts` — **ถอดข้อยกเว้นของไฟล์ท่อทิ้ง** ⇒ ไม่มีไฟล์ไหนในรีโป `.from('marketing_…')` ได้อีก | ปิดทางกลับไปแตะตารางตรง ไม่ว่าจะระบุ schema หรือไม่ |
| เทสต์ `ไฟล์ท่อห้ามพึ่ง "Exposed schemas"` — ห้ามมี `.schema(` ในไฟล์ท่อเลย | กันถอยกลับไปพึ่งค่าที่อยู่นอกรีโป |
| เทสต์เดียวกันบังคับว่าต้องมี `rpc('receive_marketing_behavior')` + `rpc('mark_marketing_behavior_archived')` จริง | กัน "เขียวเพราะไฟล์ไม่ได้ทำอะไรเลย" |
| เทสต์ `rpc ที่ไฟล์ท่อเรียก ต้องมี migration รองรับ` — อ่าน `supabase/migrations/*.sql` หา `function public.<ชื่อ>` + `grant execute … to service_role` | กันเรียก rpc ที่ไม่มีอยู่จริง และกันลืม grant (หรือ grant กว้างเกิน) |

**ยืนยันแดงจริง** (26 พ.ย. 2569): เอา `.schema()` กลับมา = แดง 2 ข้อ · ถอดบรรทัด `grant` ออกจาก
migration = แดง 1 ข้อ · คืนค่าแล้วเขียวครบ 22

## ผลที่ตามมา

- 🟢 `marketing_os` **ยังไม่ต้องเปิดให้ PostgREST มองเห็น** — พื้นที่โจมตีไม่กว้างขึ้น
- 🟢 แก้ได้โดยไม่ต้องรู้ว่าสาเหตุจริงคืออะไร (ถ้าไม่ใช่ `PGRST106` ก็ยังหาย เพราะเลี่ยงทั้งเส้นทาง)
- 🔴 **ยังไม่พิสูจน์ว่าหายจริง** — ต้องรอ event `mode:'live'` ก้อนถัดไปจากผู้ใช้จริง
  แล้ววัดที่ `archived_at` ⇒ **ห้ามเขียนว่าแก้แล้วจนกว่าจะเห็นแถวที่มีค่า**
- 🔴 2 แถวเดิมยัง `NULL` **โดยตั้งใจ** — เป็นหลักฐานชิ้นเดียวที่บอกว่าบั๊กนี้เคยเกิด
  (ไฟล์ของมันอยู่ในคลังครบแล้ว ⇒ ไม่มีข้อมูลหาย)
- ⚠️ ถ้าวันหน้าแอป OS ต้อง **อ่าน** `marketing_os` จะต้องเลือกระหว่าง "เปิด Exposed schemas +
  grant + policy" กับ "ทำ rpc อ่านเพิ่ม" — ADR นี้ไม่ได้ตัดสินข้อนั้น
- 🔴 **และทางแรกยังติดเรื่อง identity**: นับสด 26 พ.ย. 2569 — ผู้ใช้ของเขาใน
  `marketing_os.workspace_members` **11 คน มีอยู่ใน `auth.users` ของเรา 0 คน**
  ⇒ policy ที่อิง `auth.uid()` แมตช์ศูนย์แถวเสมอ · และเปิดกว้างให้ `authenticated`
  = ลูกค้าของเรา (4 บัญชี) อ่านข้อมูลการตลาดได้ทันที ⇒ **ยังเปิดทางอ่านไม่ได้จนกว่าจะตัดสินเรื่อง identity**

## ทางเลือกที่ไม่เลือก

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| เปิด `marketing_os` ใน Exposed schemas | 🟢 **พิสูจน์แล้วว่าแก้ไม่หาย** — `service_role` ไม่มี grant บนตารางเลย (0) ⇒ ต้องแก้สองที่ · แถมเปิดทั้ง schema ให้ PostgREST มองเห็น และเป็นค่าที่รีโปตรวจไม่ได้ ⇒ รอบหน้าพังแบบเดิมก็ยังไม่มีใครเห็น |
| ไม่ทำอะไร | ข้อมูลเข้าครบก็จริง แต่ผู้ใช้ได้ 503 ทุกครั้ง · client ส่งซ้ำ · และ `archived_at` โกหกว่ายังไม่เก็บคลังทั้งที่ไฟล์อยู่แล้ว |
| ถอดขั้นเก็บคลังทิ้งให้เขียว | ไฟล์อัปโหลดสำเร็จจริง — ถอดตัววัดเพื่อให้ผ่าน = ปิดตาตัวเอง (ความผิดชุดเดียวกับ ledger #36) |
| ให้ rpc คืน boolean | แยก "ลองซ้ำหลังสำเร็จ" ออกจาก "ไม่เจอแถว" ไม่ได้ ⇒ บั๊กจริงจะถูกกลบเป็นเคสปกติ |
