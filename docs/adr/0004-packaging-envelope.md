# ADR-0004 — ซองข้อมูล (packaging) เป็นรูปแบบ "ที่เก็บของเรา" ไม่ใช่รูปแบบสายส่ง

- **สถานะ**: `accepted` · **วันที่**: 20 พ.ย. 2569 · **ที่มา**: เจ้าของสั่ง "ทำ packaging ด้วย"

## บริบท

ข้อจำกัดที่ตรวจแล้วจากตัวฟังก์ชัน `marketing-track`: **รับ 1 event ต่อ 1 POST · ไม่มีโหมด batch**
⇒ ถ้าทำซองเป็น "รูปแบบสายส่ง" จะส่งไม่ได้เลย

แต่ยังต้องมีซอง เพราะคิวของค้าง (ADR-0005) ต้องเขียนลง localStorage แล้วอ่านกลับ
และการเขียน/อ่านนั้นพังได้เงียบ ๆ (เขียนไม่จบ · โควตาเต็ม · โค้ดเวอร์ชันก่อนเขียนคนละรูปแบบ)

## การตัดสินใจ

`src/lib/osPackage.ts` — ซองสำหรับ **ที่เก็บของเราเอง**: `{ v, seq, packedAt, checksum, events[] }`

- `v` = เวอร์ชันรูปแบบ · คนละเวอร์ชัน = **ทิ้งอย่างเปิดเผย** ไม่เดาความหมาย
- `seq` = ลำดับซอง ใช้บอกว่า "ซองที่ควรมีขาดไปไหม"
- `checksum` = fnv1a บน **canonical JSON (คีย์เรียงคงที่)**
  🔴 ไม่มี canonical JSON = checksum คำนวณสองครั้งได้ไม่เท่ากันทั้งที่ข้อมูลเดิม = บั๊กที่เงียบที่สุด
- แบ่งซองตาม **ทั้งจำนวน (25) และไบต์ (48KB)** — อันไหนถึงก่อนใช้อันนั้น
- `unpack()` **ไม่มีโหมดซ่อม**: checksum ไม่ตรง = ทิ้งทั้งซอง เพราะเราไม่รู้ว่าขาดอะไรไป
  เดาต่อ = สร้างข้อมูลที่ไม่มีใครเคยทำ ซึ่งแย่กว่าข้อมูลหายเพราะมันดูเหมือนจริง

⚠️ **checksum ตรวจความครบถ้วน ไม่ใช่ความปลอดภัย** — fnv1a ไม่ใช่ลายเซ็น
ใครแก้ข้อมูลในเครื่องตัวเองก็คำนวณใหม่ได้ ⇒ ของจาก outbox ยังต้องผ่าน `wireIssues()` ก่อนส่งอยู่ดี

## ผลที่ตามมา

- ✅ ที่เก็บเสียหายถูกจับได้ และแยกได้ว่า "เพี้ยน" กับ "คนละเวอร์ชัน"
- ✅ วันหน้าถ้าเขาเปิด batch เปลี่ยนแค่ชั้นส่ง ชั้นนี้ไม่ต้องแก้
- ⚠️ เพดาน 25/48KB เป็น `policy` ไม่ใช่ค่าที่พิสูจน์แล้วจากข้อมูลจริง

## ทางเลือกที่ไม่เลือก

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| เก็บเป็นอาเรย์ JSON เปล่า ๆ | ไม่รู้เวอร์ชัน ไม่รู้ว่าเสียหายไหม · อ่านของเก่าแล้วพังเงียบ |
| ใช้ SHA-256 ผ่าน WebCrypto | async ทั้งสาย เพื่อความแข็งแรงที่ไม่ได้ต้องการ (นี่ไม่ใช่งานความปลอดภัย) |
| ลายเซ็น HMAC | ต้องมีคีย์ในเครื่องผู้ใช้ = คีย์ที่ใครก็อ่านได้ ⇒ ความปลอดภัยปลอม |
| ซ่อมซองที่ checksum ไม่ตรง | เป็นการแต่งข้อมูล — ขัดกฎสูงสุดของโปรเจกต์ตรง ๆ |
