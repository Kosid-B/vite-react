# ADR-0008 — CEF: รูปแบบ event กลางหนึ่งเดียว แล้วแปลงออกทีละปลายทาง

- **สถานะ**: `accepted`
- **วันที่**: 20 พ.ย. 2569 · **ที่มา**: เจ้าของสั่ง "ทำ cmef" → ยืนยันว่าหมายถึง **Common Event Format**

## บริบท

วัดจริง 20 พ.ย. 2569: `track('…')` ที่ไม่ซ้ำกันในโค้ดที่รัน (ไม่นับ `__tests__`) = **179 ตัว**
ปลายทางที่ `analytics.track()` ส่งถึงจริง = **3 ทาง** (GA4 · Amplitude · Marketing OS)

🔴 คำถามที่ **ตอบไม่ได้เลย** ก่อนมีชั้นนี้: *"event ตัวนี้ไปถึงปลายทางไหนบ้าง"*
ต้องเปิดโค้ด 3 ที่แล้วประกอบในหัวเอง — ซึ่งเป็นรูปแบบเดียวกับที่ทำให้ Amplitude
ได้ 0 event มา ~3 เดือนโดยไม่มีใครรู้ (ledger #18): **ไม่มีใครตอบได้ว่าอะไรถึงหรือไม่ถึง**

และเมื่อ ADR-0007 ต้องยิง event จากฝั่งเซิร์ฟเวอร์ ปัญหาจะหนักขึ้นอีกชั้น:
เหตุการณ์เดียวกันจะมี **สองเส้นทางที่ประกอบ payload คนละที่** ⇒ กฎ PII มีสองมาตรฐานทันที

## การตัดสินใจ

`src/lib/eventFormat.ts` — เรกคอร์ดกลาง `CefRecord` หนึ่งรูปแบบ:
`{ schema, name, occurredAt, source, session, context, props }`

- `name` = ชื่อใน **คำศัพท์ของเราเอง** ไม่ใช่ของปลายทางไหน (นั่นคือเหตุผลที่ต้องมีชั้นนี้)
- `source: 'browser' | 'server'` — 🔴 จำเป็น เพราะ **เบราว์เซอร์อ้างความจริงเรื่องเงินไม่ได้** (ADR-0007)
- `session` = id นิรนามตัวเดียวกับ `landing_funnel.session` · **ห้ามเป็น user id**
- ตารางแปลงคำศัพท์สองฝั่ง (`EVENT_MAP` · `SENT_DIRECT` · `NOT_SENT_YET`) ย้ายมาอยู่ที่นี่
  เพราะ "ของเรา `quickcheck_*` ↔ ของเขา `calculator_*`" เป็นงานของชั้นรูปแบบ ไม่ใช่ของชั้นส่ง
- `cefToOs()` = ทางเดียวที่ประกอบ payload ของ OS · สายส่ง **ห้ามเรียก `encodeOsEvent` ตรง**

**`sinksFor(name)` ตอบคำถามข้างบนได้ และ 🔴 คำนวณจากโค้ดจริง ไม่ใช่จากรายการที่ประกาศไว้**
GA + Amplitude ได้ทุกตัวเสมอ (`track()` เรียกแบบไม่มีเงื่อนไข) · OS ได้เฉพาะที่แมป

🧮 **ไม่มีทะเบียน 179 แถวที่เขียนด้วยมือ โดยเจตนา** — ทะเบียนที่คนต้องมาเติมเอง
คือทะเบียนที่ล้าสมัยในสัปดาห์ที่สอง (ledger #85) · ให้โค้ดเป็นแหล่งความจริง แล้วให้เทสต์เฝ้า

⚠️ `landing_funnel` **ไม่นับเป็น sink ของ event** — มันเป็นตารางสถานะ 1 แถว/ผู้เข้าชม
เขียนผ่าน `track_landing` rpc คนละทาง ⇒ นับรวมเข้ามาจะอ่านผิดว่า event ทุกตัวถูกบันทึกลง DB

## ผลที่ตามมา

- ✅ ตอบได้ว่า event ไปถึงไหน โดยไม่ต้องอ่านโค้ด 3 ที่
- ✅ ท่า B (ADR-0007) ประกอบ event จากฝั่งเซิร์ฟเวอร์ด้วย **รูปแบบและกฎ PII ชุดเดียวกัน**
- ✅ เปลี่ยน/เพิ่มปลายทางในอนาคต = เพิ่มฟังก์ชันแปลงออก 1 ตัว ไม่ต้องแก้จุดที่ยิง
- ⚠️ เพิ่มชั้นกลาง 1 ชั้น ⇒ อ่านสายท่อต้องผ่าน 2 ไฟล์ (`eventFormat` → `osCodec`)
- 🔴 **ไม่ได้แก้** ปัญหาที่ 175 event ยังไม่ไปถึง OS — มันแค่ทำให้ **มองเห็นว่าไม่ไป**
  ⇒ ห้ามอ่าน ADR นี้ว่า "ข้อมูลครบแล้ว"

## ทางเลือกที่ไม่เลือก

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| ปล่อยให้แต่ละจุดยิงประกอบ payload ของแต่ละปลายทางเอง | ของเดิม · กฎ PII จะมีหลายมาตรฐานทันทีที่มีสายที่สอง |
| ทะเบียน event 179 แถวเขียนด้วยมือ (ชื่อ · คำอธิบาย · ปลายทาง) | ล้าสมัยเร็วกว่าที่จะมีประโยชน์ · และ "ปลายทาง" คำนวณได้จากโค้ดอยู่แล้ว |
| ใช้สเปกสำเร็จ (CloudEvents / CEF ของ ArcSight) | ฟิลด์ส่วนใหญ่ไม่เกี่ยวกับงานนี้ · และเราต้องการฟิลด์ `source`/`seg` ที่สเปกพวกนั้นไม่มี |
| รอทำตอนต่อท่า B | ตอนนั้นจะมีโค้ดสองสายที่ต้องรื้อพร้อมกัน = แพงกว่าทำตอนนี้ที่มีสายเดียว |
