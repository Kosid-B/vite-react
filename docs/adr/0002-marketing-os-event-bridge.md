# ADR-0002 — ส่ง event ไป Marketing OS ผ่าน edge function เท่านั้น

- **สถานะ**: `accepted`
- **วันที่**: 20 พ.ย. 2569 · **ผู้ตัดสิน**: เจ้าของ ("ลุย A ต่อ B")

## บริบท

วัดสดจากตารางของ Marketing OS เอง (20 พ.ย. 2569):

```
marketing_measurement_health_live : score 0 · reliability "unreliable" · event_count 0
                                    latest_event_at null · utm_coverage 0
marketing_measurement_config      : block_strategic_recommendations_below_score = TRUE
                                    caution_score_min 70 · reliable_score_min 90
```

⇒ **OS ปฏิเสธการให้คำแนะนำกลยุทธ์ด้วยกฎของตัวมันเอง** จนกว่าจะมี event ไหลเข้า
สาเหตุรากข้อเดียว: edge function `marketing-track` เปิดมาตั้งแต่ 23 ส.ค. 2569
แต่ `grep` ทั้ง `src/` เจอโค้ดที่เรียกมัน **0 จุด** ⇒ ท่อเปิดค้าง ~3 เดือน

ข้อจำกัดเดิมที่ขัดกัน: `CLAUDE.md` ห้ามรีโปนี้แตะอะไรของ Marketing OS ทั้งหมด (24 ส.ค. 2569)

## การตัดสินใจ

เปิดข้อยกเว้น **แคบที่สุดเท่าที่ยังทำงานได้**: ส่ง event ออกทาง
`POST /functions/v1/marketing-track` และ **อยู่ในไฟล์เดียว** `src/lib/marketingOs.ts`

- ยังห้ามทุกข้อ: `.from('marketing_…')` · เรียก rpc ของเขา · migration `marketing_*`
- `src/config.ts` เหลือแค่สวิตช์ `MARKETING_OS.live` — **ไม่รู้ชื่อปลายทาง**
  (อยากรู้ว่าเรายิงอะไรออกไป เปิดไฟล์เดียวจบ ไม่ต้องตามล่าทั้งรีโป)
- ส่งแค่ 10 event ที่ฟังก์ชันนั้นรับ · ไม่ส่งฟิลด์ UUID เลย (เราไม่มีค่าจริงของเขา)
- ใช้ `session` ตัวเดียวกับ `landing_funnel` ⇒ ข้อมูลสองฝั่ง join กันได้ภายหลัง

## 🔁 แก้ไขบริบท 20 พ.ย. 2569 (เย็นวันเดียวกัน) — สมมติฐานหลักของ ADR นี้ผิด

ADR นี้เขียนไว้ว่าการยิง `marketing-track` ทำให้ **Marketing OS มองเห็น event** · **ผิด**

เจ้าของยืนยันว่าแอป Marketing OS ชี้ไป Supabase **`bjozpwdtqbpwcxnqguka`**
แต่ `marketing-track` deploy อยู่บน **`waigsnxhrlwtiotspaim`** และใช้ `SUPABASE_URL` ของ project ตัวเอง
⇒ event ลง `marketing_events` ของ **เรา** · ฐานที่ OS อ่าน **ไม่มีตารางนั้นด้วยซ้ำ**
⇒ **ข้อมูลไม่เคยถึง OS และจะไม่ถึงด้วยท่านี้**

🔴 ความผิดเชิงวิธีคิด (ledger #94): ผมเห็นปลายทางที่มีอยู่ (`marketing-track`) + ตารางชื่อ `marketing_*`
อยู่ในฐานเรา แล้ว **สรุปว่านั่นคือปลายทางของ OS โดยไม่ได้ตรวจว่า OS อ่านฐานไหน**
— เป็นรูปแบบเดิมเป๊ะ: *เห็นของที่ดูเข้ากัน แล้วเล่าเหมือนตรวจแล้ว*

**คุณค่าที่เหลือจริงของ ADR นี้ (ยังคุ้มที่จะ merge ไว้)**
ตาราง event ชั้นละเอียดใน **ฐานของเราเอง** + VIEW `marketing_measurement_health_live`
ที่ขยับเองตามข้อมูล — ของที่เมื่อก่อนไม่มีเลย (เรามีแค่ `landing_funnel` 1 แถว/ผู้เข้าชม + GA/Amplitude)
⇒ **ห้ามอ่าน ADR นี้ว่า "เชื่อมกับ Marketing OS แล้ว"**

ทางที่ถูกอยู่ใน **[ADR-0009](0009-marketing-os-behavior-ingest.md)** — `marketing-behavior-ingest` บนฐานของเขา

## ผลที่ตามมา

- ✅ OS เริ่มมี event ⇒ health score ขยับได้ ⇒ มันเลิกบล็อกตัวเอง
- ✅ ขอบเขตเล็กพอที่จะถอนคืนได้ด้วยการปิด flag หนึ่งตัว
- ⚠️ เราเพิ่มการพึ่งพาระบบที่เราแก้โค้ดไม่ได้ (ไม่มีซอร์สในรีโปนี้) ⇒ มันเปลี่ยนสัญญาเมื่อไรเราไม่รู้ล่วงหน้า
- 🔴 **ยังตอบไม่ได้ว่า `workspace_id` ที่ hardcode ในฟังก์ชันนั้นเป็นของใคร** — ยังไม่ได้ตรวจ

## ทางเลือกที่ไม่เลือก

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| เขียนลงตาราง `marketing_*` ตรง | ข้ามเส้นแบ่งความเป็นเจ้าของเต็มตัว · และสคีมาสองฝั่งคนละชุดกัน |
| ไฟล์ส่งออกทางเดียว (export file) | เคยอนุมัติไว้ · ได้ข้อมูล**ตั้งต้น** แต่ **ส่ง event รายเหตุการณ์ไม่ได้** = ไม่แก้ `event_count 0` |
| ให้ OS ดึงจากเรา (pull) | ต้องมี endpoint สาธารณะ = rpc ใหม่ ⇒ แตะ schema ⇒ ติดด่าน (ดู ADR-0006) |
| ไม่ทำอะไรเลย | แพ้: OS บล็อกตัวเองถาวร และทุกคำแนะนำกลยุทธ์จากมันจะอ้างฐานข้อมูลที่ว่าง |
