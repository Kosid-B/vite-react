# ADR-0001 — ใช้ ADR บันทึกการตัดสินใจทางสถาปัตยกรรม

- **สถานะ**: `accepted`
- **วันที่**: 20 พ.ย. 2569
- **ผู้ตัดสิน**: เจ้าของโปรเจกต์ (สั่ง "ทำ ADR ระบบด้วย")

## บริบท

รีโปนี้มีเอกสารเยอะและละเอียด แต่ไม่มีที่ไหนตอบคำถาม **"ทำไมไม่เลือกทางอื่น"**
ผลที่วัดได้จริงจาก ledger: ข้อความอธิบายระบบเดียวกันถูกแก้กลับไปกลับมา
— เช่นสถานะตาราง `marketing_*` ที่เขียนผิด **สองรอบในทิศทางตรงข้ามกัน**
(24 ส.ค. "มีสองระบบเขียนลง" → 15 พ.ย. "0 แถวทุกตาราง" → 20 พ.ย. ของจริงคือ
มีข้อมูลตั้งต้น แต่ `marketing_events` = 0) · ledger #90

สาเหตุรากข้อเดียว: **เหตุผลของการตัดสินใจไม่ได้ถูกเก็บไว้ที่ไหนที่อ่านง่าย**
⇒ รอบถัดไปเราอ่านโค้ด แล้วสร้างเหตุผลขึ้นมาใหม่

## การตัดสินใจ

เก็บการตัดสินใจทางสถาปัตยกรรมเป็นไฟล์ `docs/adr/NNNN-<เรื่อง>.md` ไฟล์ละการตัดสินใจ
ทุกไฟล์ต้องมีหัวข้อครบ 5 ข้อ: **บริบท · การตัดสินใจ · ผลที่ตามมา · ทางเลือกที่ไม่เลือก · กลไก**

- **ทางเลือกที่ไม่เลือก** = หัวใจของ ADR · ADR ที่ไม่มีข้อนี้คือสเปกที่เขียนย้อนหลัง
- **กลไก** = เทสต์/ด่านที่ทำให้ของจริงไม่ไหลออกจากการตัดสินใจนี้
  🔴 ไม่มีกลไก = ADR กลายเป็นความตั้งใจที่ไม่มีใครบังคับ (รูปแบบความผิดเดิมของโปรเจกต์)

## ผลที่ตามมา

- ✅ การตัดสินใจรอดจาก context window
- ✅ ผู้ช่วยรอบหน้าอ่าน "ทำไม" ได้โดยไม่ต้องเดา
- ⚠️ ต้นทุน: ทุกการตัดสินใจเชิงโครงต้องเสียเวลาเขียน ~15 นาที
- ⚠️ ความเสี่ยงจริง: เขียน ADR แล้วไม่ทำตาม = เพิ่มเอกสารที่โกหก ⇒ ต้องมีเทสต์คุม

## ทางเลือกที่ไม่เลือก

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| เขียนไว้ใน `CLAUDE.md` เหมือนทุกอย่าง | ไฟล์นั้นยาวมากแล้ว และมันตอบ "ทำอะไรวันนี้" ไม่ใช่ "ทำไมเลือกทางนี้" |
| เขียนใน commit message | ค้นไม่เจอในทางปฏิบัติ · และ commit เล่าการเปลี่ยนแปลง ไม่ได้เล่าทางเลือกที่ทิ้ง |
| เพิ่มคอลัมน์ใน LESSONS-LEDGER | ledger เริ่มจาก **ความผิดพลาด** · การตัดสินใจที่ถูกตั้งแต่แรกไม่มีที่ลง |
| ไม่ทำอะไรเลย | ชนะไม่ได้ — ความผิดรูปแบบนี้เกิดแล้ว 3 รอบและกินเวลาแก้เอกสารทุกรอบ |
