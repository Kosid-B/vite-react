# ADR-0011 — รวมฐานข้อมูลเป็น Supabase project เดียว โดยแยกเป็น schema `marketing_os`

- **สถานะ**: `accepted`
- **วันที่**: 22 พ.ย. 2569
- **ผู้ตัดสิน**: เจ้าของ (*"ย้าย DB ไปอยู่ supabase เดียวกับ ceo"* + ผังสถาปัตยกรรม Core/Marketing/Security/Evidence)

## บริบท

เรามีฐานข้อมูลสองใบมาตั้งแต่ 19 ส.ค. 2569: `waigsnxhrlwtiotspaim` (ผลิตภัณฑ์) และ
`bjozpwdtqbpwcxnqguka` (Marketing OS) · ต้นทุนที่จ่ายจริงจากการแยกกัน:

🔴 **ledger #94 — ท่อที่ต่อผิดใบโดยไม่มีใครรู้ 3 เดือน**: `marketing-track` deploy บนฐาน*เรา*
แต่แอป OS อ่านฐาน*เขา* ⇒ event ที่ส่งไปไม่เคยถึงผู้อ่าน · และเรารายงานว่า "เชื่อมแล้ว" ไปรอบหนึ่ง

🔴 **ADR-0006 ขา pull ทำไม่ได้เลย** เพราะการอ่านข้ามฐานต้องใช้ service-role หรือ adapter
⇒ ทางเดียวที่เหลือคือเปิด feed สาธารณะ ซึ่งแพงกว่าปัญหาที่แก้

วัดของจริงก่อนตัดสิน (22 พ.ย. 2569 · SQL บนทั้งสองฝั่ง):
ฐานของเขามี 44 ตาราง แต่ **มีข้อมูลจริงแค่ 11 ตาราง รวม 48 แถว** · ของธุรกรรมจริงคือ
`marketing_behavior_*` 13 แถว · workspace จริง **1 ตัว** (อีก 2 ตัวชื่อ `RLS_TEST_*`)
⇒ **ขนาดของการย้ายเล็กกว่าที่กลัวกันมาก** — สิ่งที่ยากไม่ใช่ข้อมูล แต่เป็นของที่ชี้มาที่ข้อมูล

🔴 และเจอกับดักที่ทำให้ "ย้ายแบบรวมเข้า `public`" ไม่ได้: **4 ตารางชื่อซ้ำกันแต่ข้อมูลไม่เท่ากัน**
`marketing_brand_rules` เขา 7 / เรา 10 · `marketing_audience_segments` เขา 6 / เรา 5 ·
`marketing_message_pillars` 7 / 7 · `marketing_brands` 1 / 1

## การตัดสินใจ

**หนึ่ง project · แยก schema** — ของ OS ไปอยู่ `marketing_os` · `public` ยังเป็นของผลิตภัณฑ์

1. `marketing_os` ถือ 11 ตารางที่มีข้อมูล **ชื่อตารางคงเดิมทุกตัว**
   ⇒ แอป OS เปลี่ยนแค่ schema ที่เรียก ไม่ต้องไล่แก้ชื่อ 11 ที่ (จุดที่พลาดง่ายที่สุด)
2. ย้าย **ท่อ** ตามข้อมูล: `receive_marketing_behavior` + trigger `expand_marketing_behavior_batch`
   + edge function `marketing-behavior-ingest` ⇒ ยกซอร์สมาทั้งไฟล์ **เปลี่ยนแค่ schema ปลายทาง**
3. `behaviorOs.ts` เลิกใช้ `VITE_MARKETING_OS_URL`/`_ANON_KEY` ⇒ ใช้ `VITE_SUPABASE_*` ร่วมกัน
4. **ไม่มี FK ไป `auth.users`** — ผู้ใช้ของเขาไม่มีใน auth ของเรา
5. **คัดลอก ไม่ใช่ตัดทิ้ง** — ฐานเดิมยังอยู่ครบ ⇒ ย้อนกลับได้ด้วย `drop schema marketing_os cascade`

🔴 **สิ่งที่ ADR นี้ยังไม่ได้ทำ และห้ามเล่าว่าทำแล้ว**
- แอป OS **ยังชี้ไป project เดิม** (โค้ดอยู่ `D:\CEOAITHAILAND Marketing-P1.0.2-baseline` + Vercel
  `ceo-ai-marketing` ⇒ เซสชันคลาวด์เข้าไม่ถึง) ⇒ **ยังไม่ใช่การย้ายที่สมบูรณ์**
- 33 ตารางที่ว่างยังไม่สร้าง ⇒ ถ้าแอปเขาเรียกตารางเหล่านั้นจะพัง
- **identity ยังไม่รวม** ⇒ ยังไม่ใช่ "Shared Identity / Tenant Context" ตามผัง · นี่คือส่วนที่ยากจริง
- RLS policy ของเขายังไม่ยกมา (ตอนนี้ fail-closed: ไม่มี policy = ไม่มีใครอ่านได้)

## กลไก

| กลไก | กันอะไร |
|---|---|
| `supabase/migrations/0066`+`0067` | **บันทึกสิ่งที่ apply ไปแล้ว** — production เคยถูกเปลี่ยน schema โดยไม่มีร่องรอยในรีโปมาแล้ว |
| `ownershipBoundary.test.ts` อ่าน **โครงประโยค SQL** แยก schema ออกจากชื่อตาราง | `marketing_os.*` ผ่าน · `public.marketing_*` ยังถูกจับ ⇒ เส้นแบ่งย้าย ไม่ได้ยกเลิก |
| เทสต์สังเคราะห์ 4 เคสในด่านเดียวกัน | กัน "แก้ด่านให้ผ่านทุกอย่าง" — ยืนยันว่ายังจับของผิดได้จริง |
| `behaviorOs.test.ts` ห้าม `VITE_MARKETING_OS_` โผล่ในโค้ด (ตัดคอมเมนต์ก่อนตรวจ) | กันถอยกลับไปผูกกับ env ของอีก project |
| RLS เปิด + ไม่มี policy + revoke `anon`/`authenticated` | ตารางใหม่ยังไม่มีใครอ่านได้จนกว่าจะเปิดเจตนา |
| rpc `grant execute` ให้ `service_role` เท่านั้น | ท่อเข้าได้ทางเดียว คือผ่าน edge function |

**พิสูจน์แล้วว่าเดินจริง** (22 พ.ย. 2569): เรียก rpc ด้วย batch ทดสอบ → trigger กาง event ออกมาจริง
→ ลบของทดสอบ → นับกลับเป็น 5/4/3 เท่าเดิม · 🔴 **ครึ่ง HTTP ยังตรวจไม่ได้จากเซสชันนี้**
(egress proxy ปฏิเสธโฮสต์ Supabase ของเรา — 403 CONNECT) ⇒ ยืนยันได้จาก **โค้ดที่เหมือนเดิมทั้งไฟล์**
และต้องวัดซ้ำด้วย `mode:'live'` ที่เข้ามาจริงบน production

## ผลที่ตามมา

- 🟢 ไม่ต้องมี cross-project adapter หรือ service-role ข้ามฐานอีก (เหตุผลที่เจ้าของยกมา)
- 🟢 ADR-0006 (ขา pull) ทำได้ง่ายขึ้นมาก — ข้อมูลอยู่ฐานเดียวกับผู้อ่านแล้ว
- 🔴 **"ไม่มีด่านกั้น" ≠ "ทำแล้ว"** — ขา pull ยังไม่มีใครสร้าง
- 🔴 ความเสี่ยงใหม่ที่รับไว้: `marketing_os` อยู่ใน production เดียวกับข้อมูลลูกค้า ⇒ **tenant isolation
  ต้องตรวจทุกครั้ง** (เจ้าของเขียนข้อนี้ไว้ในผังเอง) · วันนี้กันด้วย fail-closed ไม่ใช่ด้วย policy ที่ถูก
- ⚠️ Secret/Variable `VITE_MARKETING_OS_*` ใน GitHub กลายเป็นของไม่ได้ใช้

## ทางเลือกที่ไม่เลือก

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| รวมลง `public` ตรง ๆ | 4 ตารางชื่อซ้ำข้อมูลไม่เท่ากัน ⇒ ต้องเลือกว่าข้อมูลฝั่งไหนตาย = ข้อมูลหายโดยการตัดสินใจของผู้ช่วย |
| เปลี่ยนชื่อตารางตอนย้าย (ตัดคำ `marketing_` ออก) | แอป OS ต้องแก้ 11 ที่ ⇒ พลาดที่เดียวก็เงียบ · ได้ความสวยแลกกับความเสี่ยง |
| คงสองฐานไว้แล้วทำ read adapter | คือสิ่งที่เจ้าของสั่งเลิกทำโดยตรง · และเป็นต้นเหตุของ ledger #94 |
| ย้ายแบบ **ตัด** (ลบของเดิมทันที) | แอป OS ยังชี้ฐานเดิม ⇒ ตัดคือทำของเขาล่มทันที · และย้อนกลับไม่ได้ |
| สร้างครบ 44 ตารางเลย | 33 ตารางที่ว่างไม่มี DDL ที่พิสูจน์ได้ว่าแอปเขาใช้จริง ⇒ เดาโครงสร้าง = หนี้ที่ไม่มีใครตรวจ |
