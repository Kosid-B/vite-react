# ADR-0015 — identity ของแอป Marketing OS: ทาง (ก) service key แบบจำกัดขอบ

- **สถานะ**: `superseded`
- **แทนด้วย**: [ADR-0016](0016-identity-shared-auth-users.md) — เจ้าของเปลี่ยนเป็น (ข)
  หลังวัดได้ว่าเป็นผู้ใช้จริง **1 คน** ที่ **มีบัญชีในฐานเราอยู่แล้ว** ⇒ ต้นทุนของ (ข) หายไป
  🔴 **ไม่แก้เนื้อหาเดิมด้านล่างย้อนหลัง** — เก็บไว้เพื่อให้เห็นว่าตัดสินบนข้อมูลชุดไหน
- **วันที่**: 26 พ.ย. 2569
- **ผู้ตัดสิน**: เจ้าของ (*"ก"*) — เลือกจาก 3 ทางที่เสนอ
- **ขอบเขตของ ADR นี้**: การ **เลือกทาง** + **ตัวเลขที่วัดได้** + **สัญญาที่ต้องทำตาม**
  🔴 **ไม่รวมการลงมือในโค้ดแอป OS** ซึ่งอยู่ในอีก codebase บนเครื่องเจ้าของ (ยังไม่ได้ทำ)

## บริบท

หลัง ADR-0014 ตารางครบ 17/17 แล้ว ด่านที่เหลือข้อเดียวคือ **แอปอ่านข้อมูลไม่ได้**
เพราะ `anon`/`authenticated` มี 0 grants บน `marketing_os` และผู้ใช้ของแอปไม่มีใน `auth.users` ของเรา

สามทางที่เสนอ: **(ก)** ฝั่งเซิร์ฟเวอร์ใช้ service key + เขียนการตรวจ workspace ในโค้ดเอง ·
**(ก) จำกัดขอบ** เหมือน (ก) แต่บังคับให้ทุก query ผ่าน helper ตัวเดียว ล็อกด้วยเทสต์ ·
**(ข)** ย้ายผู้ใช้เข้า `auth.users` ของเรา แล้วเขียน RLS

### 🔴 ข้อมูลใหม่ที่วัดได้ **หลัง** เจ้าของตัดสิน — ตัวเลข "11 คน" เข้าใจผิดมาตลอด

`CLAUDE.md` · ADR-0012 · ADR-0013 · ADR-0014 เขียนไว้ว่า *"ผู้ใช้ของเขา 11 คน"*
อ่านแล้วเข้าใจว่าเป็นคนจริง 11 คนที่ต้องย้าย ⇒ ทำให้ทาง (ข) ดู**แพง** ตลอดการตัดสินทุกรอบ

วัดสด 26 พ.ย. 2569 **ยืนยันสองฝั่ง (ฐานเขาและฐานเรา ตรงกันทุกแถว)**:

| workspace | สร้างเมื่อ | สมาชิก | brand | segment | rule |
|---|---|---|---|---|---|
| `RLS_TEST_WORKSPACE_A` | 24 ส.ค. 2569 07:55:01 | 5 | 0 | 0 | 0 |
| `RLS_TEST_WORKSPACE_B` | 24 ส.ค. 2569 07:55:01 | 5 | 0 | 0 | 0 |
| **`ceo-ai-thailand`** (`e82e7d93…`) | 4 ก.ย. 2569 | **1** | 1 | **6** | **7** |

🔴 **ผู้ใช้จริง = 1 คน · อีก 10 คนเป็น fixture ของเทสต์ RLS**
(สอง workspace นั้นสร้าง**วินาทีเดียวกัน** ชื่อบอกตัวเองว่าเป็นเทสต์ และ **ว่างเปล่าทั้งคู่**)
🟢 `e82e7d93…` คือ workspace **ตัวเดียวกับที่ `marketing-behavior-ingest` hardcode ไว้**
⇒ **แอป OS วันนี้เป็น single-tenant ของเจ้าของ** ไม่ใช่ระบบหลายผู้ใช้
⇒ **ต้นทุนของทาง (ข) = 1 บัญชี ไม่ใช่ 11** ⇒ เหตุผลหลักที่เคยปัดตก (ข) หายไป

⚠️ ข้อมูลนี้มาถึง **หลัง** การตัดสิน ⇒ ADR นี้ยังบันทึก (ก) ตามที่เจ้าของเลือก
และยกเรื่องนี้ให้เจ้าของพิจารณาว่าจะเปลี่ยนไหม — **ถ้าเปลี่ยน ให้เขียน ADR-0016 มา superseded ตัวนี้
ไม่ใช่แก้ไฟล์นี้ย้อนหลัง**

## การตัดสินใจ

**ใช้ (ก) แบบจำกัดขอบ** — service key อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น และทุก query ต้องผ่านประตูเดียว

สัญญา 6 ข้อที่โค้ดแอป OS ต้องทำตาม:

1. `SUPABASE_SERVICE_ROLE_KEY` **ห้ามมีคำนำหน้า `NEXT_PUBLIC_`** และห้ามถูกอ้างในไฟล์ที่ส่งถึงเบราว์เซอร์
2. **ไฟล์เดียวเท่านั้น** ที่อ่าน env ตัวนั้นได้ (ประตู) — ไฟล์อื่นเรียก `createClient` ด้วย service key ไม่ได้
3. ทุกฟังก์ชันข้อมูลรับ `workspaceId` เป็นพารามิเตอร์แรก และประตูเป็นผู้ใส่
   `.eq('workspace_id', workspaceId)` ให้ทุก query — ผู้เรียกใส่เองไม่ได้
4. `workspaceId` ต้องมาจาก **ฝั่งเซิร์ฟเวอร์** (session หรือค่าคงที่ของระบบ)
   🔴 **ห้ามรับจาก query string / path / body ของผู้ใช้** — นั่นคือรูที่ทำให้ (ก) กลายเป็นเปิดหมด
5. ประตูต้องปฏิเสธถ้า `NEXT_PUBLIC_SUPABASE_URL` ชี้ไป `bjozpwdtqbpwcxnqguka` (project ที่เลิกใช้)
6. 🔴 **เรื่องล็อกอินยังไม่ถูกแก้ด้วย ADR นี้** — ผู้ใช้จริง 1 คนนั้นยังไม่มีใน `auth.users` ของเรา
   ⇒ (ก) ทำให้ **อ่านข้อมูลได้** แต่ไม่ได้ทำให้ **ล็อกอินได้** · ต้องตัดสินแยก (ดู ผลที่ตามมา)

## กลไก

| กลไก | กันอะไร |
|---|---|
| `osRepointReadiness.IDENTITY_FACTS` — ล็อก 3 workspace / 11 สมาชิก / **ผู้ใช้จริง 1** / fixture 10 / ใน `auth.users` ของเรา 0 · พร้อมวันที่ | กันไม่ให้ใครกลับไปอ้าง "11 คน" เป็นคนจริง · เทสต์บังคับ `realMembers + fixtureMembers === membersTotal` และ `realMembers < membersTotal` |
| เทสต์อ่าน **CLAUDE.md ตัวจริง**: ห้ามมีบรรทัดที่พูดถึง `workspace_members` คู่กับ "11 คน" เว้นแต่บรรทัดนั้นประกาศว่า "เคยเขียน" ผิด | กันความผิดเดิมกลับมาทางเอกสาร ซึ่งอยู่ต่อแม้บทสนทนาหายไป (ledger #41) |
| `IDENTITY_APPROACH = 'service_key_scoped'` + `IDENTITY_IMPLEMENTED = false` แยกกัน · เทสต์บังคับว่าข้อความ blocker ต้องพูดว่า **"เลือกทางแล้ว"** ไม่ใช่ **"ยังไม่ตัดสิน"** | กันสองความผิดคนละทาง: อ้างว่ายังไม่ตัดสินทั้งที่ตัดสินแล้ว · และอ้างว่าเสร็จทั้งที่ยังไม่ได้ทำ |
| `osRepointReady()` คืน `false` จนกว่า `IDENTITY_IMPLEMENTED` จะเป็น `true` | ห้ามใครเขียนว่าข้อ ① เสร็จ ก่อนมีหลักฐาน |
| `ownershipBoundary.test.ts` (ADR-0013) ยังบังคับอยู่ครบ | (ก) ไม่ได้ขออะไรจาก `anon`/`authenticated` ⇒ ด่านนี้ต้องไม่ถูกผ่อน |

🔴 **กลไกที่ยังทำไม่ได้ และต้องบอกว่าเพราะอะไร**: สัญญา 6 ข้อข้างบนบังคับใน **อีก repo**
ซึ่งเซสชันคลาวด์เปิดไม่ได้ (`not_available`) ⇒ รีโปนี้เขียนสัญญาได้ แต่ **บังคับให้เป็นจริงไม่ได้**
⇒ เทสต์ที่ล็อกข้อ 1–5 ต้องไปอยู่ใน repo ของแอป OS · **ตราบที่ยังไม่มี ข้อ (ก) พึ่งวินัยคน ไม่ใช่กลไก**

## ผลที่ตามมา

- 🟢 แอปอ่าน `marketing_os` ได้ โดยไม่ต้องแตะสิทธิ์ของ `anon`/`authenticated` เลย
- 🟢 ย้อนกลับได้: เลิกใช้ service key = แอปอ่านไม่ได้เหมือนเดิม · ไม่มีอะไรในฐานถูกเปลี่ยน
- 🔴 **service key ข้าม RLS ทั้งหมด** — ความถูกต้องของเส้นแบ่ง workspace ย้ายจาก Postgres ไปอยู่ที่โค้ด
  ⇒ พลาดจุดเดียวในข้อ 3 หรือ 4 = คนหนึ่งเห็นทุก workspace · นี่คือราคาที่ (ก) จ่าย
- 🔴 **ล็อกอินยังไม่ถูกแก้** — ต้องเลือกต่ออีกชั้น: สร้าง **1 บัญชี** ในของเรา ·
  ให้แอปล็อกอินผ่าน project เดิมแต่อ่านข้อมูลจากของเรา · หรือไม่มีล็อกอินเลยเพราะเป็น single-tenant
  ⇒ 🟡 **ยังไม่รู้ว่าแอปล็อกอินอย่างไรวันนี้** เพราะยังไม่เคยเห็นโค้ดส่วนนั้น
- 🟡 **ยังไม่ได้ทดสอบว่าแอปอ่านได้จริง** · เกณฑ์: `marketing_audience_segments` ต้องได้ **6** (ของเขา)
  ไม่ใช่ **5** (ของเรา) + ยืนยันซ้ำด้วยรหัสกลุ่ม `growth`/`employee` ไม่ใช่ `owner`/`sidebiz`
- ⚠️ **ถ้าวันหน้ามีผู้ใช้จริงมากกว่า 1 คน** ต้องกลับมาทบทวน ADR นี้ทันที — เหตุผลที่ (ก) พอใช้วันนี้
  คือ **single-tenant** ไม่ใช่เพราะ (ก) ปลอดภัยโดยตัวมันเอง

## ทางเลือกที่ไม่เลือก

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| **(ข) ย้ายผู้ใช้เข้า `auth.users` ของเรา + เขียน RLS** | เจ้าของเลือก (ก) · 🔴 **แต่หลังตัดสินแล้ววัดได้ว่าเป็น 1 บัญชี ไม่ใช่ 11** ⇒ เหตุผลเรื่องต้นทุนที่เคยทำให้ปัดตกไม่จริงอีกต่อไป และทาง (ข) ให้ Postgres บังคับเส้นแบ่งแทนโค้ด ⇒ **ยกให้เจ้าของพิจารณาเปลี่ยน (ADR-0016)** |
| **(ก) แบบไม่จำกัดขอบ** (service key แล้วเขียนตรวจกระจายทุกไฟล์) | เส้นแบ่งความปลอดภัยที่กระจายอยู่หลายไฟล์ = พลาดที่ไหนก็ไม่มีใครเห็น · ประตูเดียวทำให้เหลือจุดที่ต้องตรวจจุดเดียว |
| สร้าง role เฉพาะใน Postgres + RLS อิง `current_setting()` แล้วต่อผ่าน JWT ที่เซ็นเอง | แข็งแรงกว่าทั้ง (ก) และ (ข) เพราะฐานบังคับเอง **แต่ต้องใช้ JWT secret ของ project และทดสอบจริง** ซึ่งเซสชันนี้ทำไม่ได้ (proxy block `supabase.co`) ⇒ เสนอเป็นโค้ดที่ไม่เคยรัน = ผิด skill `shipped-not-written` |
| เปิด grant ให้ `authenticated` ไปเลย | ซ้ำกับที่ ADR-0013 ปัดตกแล้ว · และวันนี้ผู้ใช้จริงยังไม่มีใน `auth.users` ⇒ ไม่ได้ช่วยเขา แต่เปิดให้ลูกค้าเราอ่านได้ |
