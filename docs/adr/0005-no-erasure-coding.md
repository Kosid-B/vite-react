# ADR-0005 — ไม่ใช้ erasure coding · ใช้สำเนาฝั่งเรา + ส่งซ้ำ + นับของหาย

- **สถานะ**: `rejected` (ปฏิเสธ *กลไก* erasure coding · **ไม่ได้ปฏิเสธเป้าหมาย** คือกันข้อมูลหาย)
- **วันที่**: 20 พ.ย. 2569
- **ที่มา**: เจ้าของสั่ง "สร้าง Erasure coding ที่จำเป็น"

## บริบท

สายท่อส่ง event ไป Marketing OS (ADR-0002) ทำงานแบบยิงแล้วไม่สนใจผล
⇒ เน็ตหลุด / ปลายทาง 5xx / ผู้ใช้ปิดแท็บ = **event หายถาวรและไม่มีใครรู้ว่าหาย**
นี่คือรูปแบบความผิดเดิมของโปรเจกต์: Amplitude ได้ 0 event มา ~3 เดือนโดยไม่มีใครรู้ (ledger #18)

คำสั่งคือ "สร้าง erasure coding ที่จำเป็น" ⇒ ต้องตอบก่อนว่า **จำเป็นจริงไหม**

## การตัดสินใจ

**ไม่ใช้ erasure coding** และ**ไม่เรียกสิ่งที่สร้างว่า erasure coding**

erasure coding (Reed–Solomon k-of-n) แก้ปัญหาเฉพาะแบบ: ข้อมูลถูกหั่นเป็น n ชิ้น
กระจายไว้หลายที่ หายไปได้ถึง n−k ชิ้นแล้วยังคำนวณกลับมาครบ
เงื่อนไขที่ทำให้มันได้ผลมี 2 ข้อ และ **ระบบนี้ไม่เข้าทั้งสองข้อ**:

| เงื่อนไขที่ erasure coding ต้องการ | ของเราจริง ๆ |
|---|---|
| หน่วยที่หายคือ **ชิ้นส่วน** ของข้อมูล | หน่วยที่หายคือ **POST ทั้งก้อน** (ไม่มีชิ้นส่วนเหลือให้คำนวณ) |
| ชิ้นส่วนอยู่ **หลายที่ที่พังไม่พร้อมกัน** | ที่เก็บมีที่เดียว (localStorage ของเครื่องนั้น) ⇒ parity หายพร้อมข้อมูลเสมอ |

⇒ ใส่ parity = เปลืองที่เก็บและเวลา CPU โดย**กู้อะไรกลับมาไม่ได้เลยแม้แต่กรณีเดียว**

**สิ่งที่สร้างแทน (3 ชั้น · `src/lib/osOutbox.ts`)**

1. **สำเนาฝั่งเรา = redundancy ตัวจริง** — `landing_funnel` · `quickcheck_submissions` ·
   `client_errors` เป็นตารางของเราเอง ส่งไป OS ไม่ถึงก็ยังมีต้นฉบับ ⇒ เล่าซ้ำได้
2. **ส่งซ้ำ (replay)** — ที่ส่งไม่ถึงค้างในคิว ส่งใหม่รอบที่ผู้ใช้กลับเข้าเว็บ
3. **นับของหายแยกตามเหตุผล** (`invalid` · `overflow` · `corrupt` · `version`)
   🔴 ข้อนี้สำคัญที่สุด: กู้ไม่ได้ยังรับได้ แต่ **หายแล้วไม่รู้ตัว** ทำให้ตัวเลขทุกตัวข้างหน้า
   กลายเป็นคำโกหกโดยการละเว้น · และตัวนับต้อง**แยกเหตุผล** เพราะทางแก้คนละทาง
   (`corrupt` = บั๊กที่เก็บ · `version` = ต้องย้ายรูปแบบ · `overflow` = เพดานต่ำเกิน)

ส่วน `checksum` ในซอง (ADR-0004) จับได้แค่ "ข้อมูลเพี้ยน/ขาด" — **ไม่ใช่ความซ้ำซ้อน
และไม่ใช่ความปลอดภัย** (fnv1a ไม่ใช่ลายเซ็น · ใครแก้ข้อมูลในเครื่องตัวเองก็คำนวณใหม่ได้)

## ผลที่ตามมา

- ✅ event ที่ส่งไม่ถึงไม่หายทันที — ได้โอกาสส่งใหม่
- ✅ ของที่หายจริงมีตัวเลขกำกับ อ่านได้ว่าหายกี่ชิ้นเพราะอะไร
- 🔴 **ยังหายได้จริงใน 2 กรณี และยอมรับแล้ว**: ① ผู้ใช้ไม่กลับมาอีกเลย
  ② เบราว์เซอร์ปิด storage (โหมดส่วนตัว) ⇒ `browserStore()` คืน `null` = หายทันที
  ⇒ **ห้ามอ้างว่าสายท่อนี้ไม่มีข้อมูลหาย**
- ⚠️ เพดานคิว 100 ชิ้น · เกินแล้วทิ้ง**ตัวเก่าสุด** (ของเก่าที่มาช้าเกินใช้ตัดสินใจไม่ได้อยู่แล้ว)

## ทางเลือกที่ไม่เลือก

| ทางเลือก | คะแนน | ทำไมไม่เลือก |
|---|---|---|
| Reed–Solomon parity บน event ในคิว | 0/5 | กู้ไม่ได้แม้กรณีเดียว (เหตุผลในตารางด้านบน) · เพิ่มโค้ดที่ต้องดูแลฟรี ๆ |
| เก็บคิวไว้ใน DB ของเราก่อนส่งต่อ | 3/5 | ได้ความทนทานจริง **แต่ต้องมีตารางใหม่ = แตะ schema** ⇒ ติดด่าน `releaseGates` |
| ยิงซ้ำทันทีในหน้าเดิม (retry + backoff) | 2/5 | ไม่ช่วยกรณีที่พบบ่อยที่สุด (ผู้ใช้ปิดแท็บ) และเปลืองแบตผู้ใช้ |
| **คิวในเครื่อง + ส่งซ้ำ + นับของหาย** | **4/5** | ✅ เลือก — ไม่แตะ schema · กู้ได้กรณีที่พบบ่อย · ที่กู้ไม่ได้ก็ยังรู้ตัวเลข |
| ไม่ทำอะไรเลย | 1/5 | แพ้ เพราะไม่รู้ด้วยซ้ำว่าหายไปเท่าไร = ความผิดเดิมของ Amplitude ซ้ำรอบที่สอง |
