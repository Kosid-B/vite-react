## 0. สรุปให้ผู้บริหารอ่าน 30 วินาที

1. **กลยุทธ์ของคุณถูกทาง** — เจาะคนที่เริ่มธุรกิจก่อน แล้วค่อยขาย ISO ตอนเขาโต เป็น land-and-expand
   ที่ประหยัดกว่าการให้ B.Training ไปแย่งลูกค้าที่ปรึกษาหน้าใหม่จริง (เหตุผลเชิงตัวเลขอยู่ข้อ 4)
2. ⚠️ **แต่ "Gen X/Y/Z" ยังไม่ใช่กลุ่มเป้าหมายที่ใช้งานได้** — มันคือช่วงอายุ ไม่ใช่กลุ่มคนที่มีปัญหาเดียวกัน
   Gen Y อายุ 28–43 มีทั้งคนเพิ่งเริ่มและคนทำมา 15 ปี ซึ่งซื้อคนละเหตุผล (ข้อ 3)
3. 🔴 **ตัวเลขสัดส่วนประชากรรายเจนที่เรามีอยู่ ยังตามกลับไปต้นทางไม่ได้** — ต้นทางเป็นสื่อ
   และโดเมนถูกบล็อกจากเครื่องที่ตรวจ (ข้อ 2) · ห้ามเอาไปใส่คอนเทนต์จนกว่าจะยืนยัน
4. ✅ **สิ่งที่ลงมือแล้ววันนี้:** เก็บข้อมูล first-party ของเราเอง (ตาราง `quickcheck_submissions`)
   ซึ่งจะตอบว่ากลุ่มเป้าหมายจริงคือใคร โดยไม่ต้องพึ่งสัดส่วนประชากรจากสื่อเลย

## 2. 🔴 ตัวเลขที่ **ยังใช้ไม่ได้** — สัดส่วนรายเจน

`skill/market-insight-thailand` ของเราเองระบุไว้ว่า:

| Generation | สัดส่วนที่ skill ระบุ | สถานะการตรวจ |
|---|---|---|
| Baby Boomer | 16% | 🔴 ตามต้นทางไม่ถึง |
| Gen X | 24% | 🔴 ตามต้นทางไม่ถึง |
| Gen Y | 23% | 🟡 ใกล้เคียงแหล่งอื่น (22% ปี 2566) |
| Gen Z | 20% | 🔴 ตามต้นทางไม่ถึง |

**เหตุผลที่ยังใช้ไม่ได้ (3 ข้อ):**

1. **ต้นทางที่ skill อ้างคือ MarketThink = สื่อ** ซึ่งตามกฎ `thai-market-data-sources` ของเราเอง
   อยู่ชั้นล่างสุด (ข้อมูลรัฐ > รายงานเอกชน > สื่อ) และกฎบังคับว่า *"ถ้าตามไม่ถึงต้นทาง = ยังใช้ไม่ได้"*
2. **โดเมนถูกบล็อกจากเครื่องที่ตรวจ** (marketthink.co, sanook.com → EGRESS_BLOCKED)
   จึงเปิดอ่านตัวเลขต้นทางไม่ได้ — ตามกฎ `data-verification-10-rules` เพดานความเชื่อถือจึงเป็น 🟡
3. **ตัวเลขบวกกันได้แค่ 83%** (16+24+23+20) ที่เหลือ 17% ไม่ระบุว่าเป็นใคร
   (น่าจะเป็น Gen Alpha + รุ่นก่อน Boomer แต่ **นี่คือการเดาของผม ไม่ใช่ข้อมูล**)

**สิ่งที่หาเจอจากภายนอกและระบุที่มาได้ 🟡:**
- Gen X (44–59 ปี) + Gen Y (28–43 ปี) รวมกัน **30.9 ล้านคน ≈ 60% ของผู้มีสิทธิเลือกตั้ง**
  ⚠️ **เป็น % ของผู้มีสิทธิเลือกตั้ง ไม่ใช่ % ของประชากรทั้งหมด** — คนละฐาน ห้ามเอาไปสลับกัน
- Gen Y > 14.57 ล้านคน = 22% ของคนไทย (ข้อมูลปี 2566 — เก่ากว่าที่เราต้องการ 3 ปี)

## 3. ⚠️ ปัญหาเชิงวิธีคิด: "Gen" ไม่ใช่กลุ่มเป้าหมาย

นี่คือข้อที่ผมคิดว่าสำคัญกว่าตัวเลขทั้งหมดข้างบน

**Gen Y อายุ 28–43 ปี** — ในช่วงนี้มีทั้ง:
- คนอายุ 28 เพิ่งลาออกจากงานประจำ ยังไม่มีลูกค้าสักคน → เจ็บเรื่อง *"จะเริ่มยังไง"*
- คนอายุ 43 ทำธุรกิจมา 15 ปี มีพนักงาน 20 คน → เจ็บเรื่อง *"โตแล้วคุมไม่อยู่"*

**สองคนนี้ต่างกันมากกว่าคนอายุ 28 กับ 25 เสียอีก** — การยิงข้อความชุดเดียวกันไปทั้ง "Gen Y" จึงไม่โดนทั้งคู่

### เกณฑ์แบ่งที่ใช้งานได้จริง — แบ่งตาม "ระยะของธุรกิจ" ไม่ใช่ปีเกิด

| ระยะ | เขาเจ็บเรื่องอะไร | เข้าระบบเราทางไหน | ต่อยอดเป็น ISO ได้เมื่อไหร่ |
|---|---|---|---|
| **ยังไม่เริ่ม** | กลัวเจ๊ง ไม่รู้จะเริ่มตรงไหน | ตรวจสินค้าเร็ว → Roadmap 15 วัน | ยังอีกไกล (3–5 ปี) |
| **เพิ่งเริ่ม (0–2 ปี)** | หาลูกค้าไม่ได้ · ตั้งราคาไม่เป็น | ตั้งราคา · การตลาด | ยังไม่ถึง |
| **โตแล้วเริ่มมั่ว (3–7 ปี)** | คุมงานไม่ทัน · พึ่งความจำ | ทะเบียนกระบวนการ | 🎯 **จุดที่ ISO เริ่มขายได้** |
| **ต้องใช้ ISO แล้ว** | ลูกค้า/คู่ค้าบังคับ | หน้าประเมิน ISO | 🎯 **ส่งต่อ B.Training ทันที** |

> อายุใช้เป็นข้อมูลรอง (เลือกช่องทางสื่อ / โทนภาษา) ได้ — แต่ **ห้ามใช้เป็นตัวแบ่งกลุ่มเป้าหมายหลัก**

## 4. กลยุทธ์ของคุณ — ตรวจแล้วว่าสมเหตุสมผล

> *"ถ้าเขาทำธุรกิจแล้วโต เขาจะเชื่อใจให้เราทำ ISO ต่อ เพราะถ้าให้ B.Training ไป get ลูกค้าที่ปรึกษาใหม่
> แข่งกับคู่แข่ง ต้องใช้ทรัพยากรและเวลาสูง — นี่เป็นประสบการณ์ตรงจากผม"*

ตรวจกับตัวเลขที่มี — **ข้อสรุปนี้แข็งแรง**:

| | ทาง A: B.TC หาลูกค้าที่ปรึกษาใหม่โดยตรง | ทาง B: SaaS ก่อน → ISO ทีหลัง |
|---|---|---|
| คู่แข่ง | ที่ปรึกษา ISO ทุกเจ้าในไทย ชนกันที่ราคาและสายสัมพันธ์ | น้อยกว่ามาก (แทบไม่มีใครทำ SaaS วางระบบภาษาไทย) |
| ต้นทุนต่อดีล | สูง (เยี่ยมลูกค้า เสนองาน ประมูล) | ต่ำ (ระบบทำงานเอง) |
| ความไว้ใจตอนขาย ISO | ต้องสร้างใหม่ทั้งหมด | **มีอยู่แล้ว — เขาใช้ระบบเรามาหลายปี** |
| เวลาเห็นผล | เร็ว (เดือน) | ช้า (ปี) ⚠️ |
| ความเสี่ยง | แข่งราคาจนกำไรบาง | **ลูกค้าอาจไม่โตถึงจุดที่ต้องใช้ ISO** ⚠️ |

**ความเสี่ยงที่ต้องรู้:** ธุรกิจที่เริ่มใหม่ส่วนใหญ่ไม่โตถึงจุดที่ต้องทำ ISO
ถ้าใน 100 คนที่ใช้ระบบเรา มี 3 คนที่โตถึงจุดนั้นใน 5 ปี — ทาง B จะคุ้มก็ต่อเมื่อ
**ตัว SaaS เลี้ยงตัวเองได้ระหว่างทาง** ไม่ใช่ขาดทุนรอ ISO

⇒ **SaaS ต้องทำกำไรได้ในตัวมันเอง และ ISO คือโบนัส ไม่ใช่แผนหลัก**
ถ้าคิดกลับกัน (ยอมขาดทุน SaaS เพื่อรอดีล ISO) จะกลายเป็นการอุดหนุนที่ไม่มีวันจบ

**สิ่งที่ต้องวัดเพื่อพิสูจน์กลยุทธ์นี้:** จำนวนผู้ใช้ที่เดินจาก "เพิ่งเริ่ม" → "โตแล้วมั่ว"
ในระบบเรา · ระบบเก็บข้อมูลนี้ได้แล้วผ่าน `visitedPages` + `roadmapProgress()`

## 5. ✅ สิ่งที่สร้างเสร็จแล้ววันนี้ — เลิกเดา เริ่มวัด

**ตาราง `quickcheck_submissions` + แผงในหน้า admin** (migration 0056 · apply ที่ production แล้ว)

เก็บจากคนที่กรอก "ตรวจสินค้าเร็ว" บนหน้าแรก:
- ประเภทธุรกิจ (dropdown) · ราคา/ต้นทุน/ยอดขาย/ค่าใช้จ่ายคงที่
- **หัวข้อที่กดดูลึก ← ตัวสำคัญที่สุด: บอกว่าเขากังวลเรื่องอะไรจริง**
- ผลสรุป (ขาดทุน/กำไรบาง/ปกติ) · กดเปิดพื้นที่ทำงานหรือไม่

**PDPA — ตัดสินใจแล้วและมีเทสต์บังคับ:**
- ❌ **ไม่เก็บชื่อสินค้าที่ผู้ใช้พิมพ์** (free text อาจมีชื่อร้าน/เบอร์) — อยู่ใน localStorage เครื่องเขาเท่านั้น
- มีเทสต์ยืนยันว่า payload ที่ส่งขึ้น server ไม่มีชื่อสินค้าแม้ผู้ใช้กรอกมา
- RLS ปิด + ไม่มี policy + **ตัด GRANT ระดับตารางของ anon ออก** (ดูข้อ 6)

**เกณฑ์กันอ่านผลเร็วเกิน:** ต้องมีคนกดหัวข้ออย่างน้อย **30 คน** แผงถึงจะบอกว่าอันดับเชื่อได้
(บทเรียนจากเคส 15 ส.ค. ที่เคยสรุปจากคน 60 คนแล้วผิด)

## 6. 🔒 ช่องโหว่ที่เจอระหว่างทำ และปิดแล้ว

ตรวจสิทธิ์บนฐานข้อมูลจริงหลัง apply migration พบว่า:

```
quickcheck_submissions : anon SELECT = true · RLS = on · policy = 0
landing_funnel (0051)  : anon SELECT = true · RLS = on · policy = 0   ← ของเดิมก็เป็น
```

RLS เปิดและไม่มี policy → anon อ่านได้ 0 แถวจริง **ข้อมูลยังไม่รั่ว**
แต่ **GRANT ระดับตารางยังค้างอยู่จาก default ของ Supabase** — ถ้าวันหน้ามีใครเผลอเพิ่ม policy
เข้าไปตัวเดียว ข้อมูลจะรั่วทันทีโดยไม่มีอะไรกั้น

**แก้แล้ว:** `revoke all on table … from anon, authenticated` ทั้งสองตาราง
(ตรวจก่อนว่าไม่มีโค้ดไหนเข้าถึงตารางตรง — ทุกทางผ่าน RPC security definer)
ยืนยันหลังแก้: `anon SELECT = false` ทั้งคู่ · เขียนผ่าน RPC ยังทำงานปกติ
