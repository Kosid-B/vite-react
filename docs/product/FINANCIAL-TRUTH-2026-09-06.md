## ชั้นความจริง — แกนที่สาม ไม่ใช่ taxonomy ซ้ำ

รีโปมี 2 แกนอยู่แล้ว · ไฟล์นี้เพิ่มแกนที่ **ถามคนละคำถาม**:

| แกน | ถามว่า |
|---|---|
| `decisionRules.ThresholdStatus` | *เกณฑ์นี้พิสูจน์แล้วหรือยัง* (policy/hypothesis/validated) |
| `positioningEngine.ClaimStatus` | *คำกล่าวอ้างนี้เชื่อได้แค่ไหน* (hypothesis→validated) |
| **`financialTruth.TruthLevel`** | **ตัวเลขนี้มาจากไหน** (measured/derived/assumed/placeholder/unavailable) |

### กลไกหลัก: ค่าที่คำนวณ แข็งแรงกว่าวัตถุดิบที่อ่อนที่สุดไม่ได้

```ts
derive('ltv', …, [measured(100), assumed(0.5)], ([a,b]) => a*b)
// → value: 50   (สูตรถูก)
// → level: 'assumed'   ⇒ showAsActual() = false
```

🔴 **นี่คือสิ่งที่ทำให้คำสั่ง "ห้ามเอา ASSUMED ไปแสดงเหมือนเป็น Actual" บังคับใช้ได้จริง**
ไม่ใช่ข้อตกลงที่คนต้องจำ — LTV ที่คำนวณจาก renewal 50% ที่เราเดาเอง
**ตกชั้นเป็น "สมมติ" โดยอัตโนมัติ** ต่อให้สูตรถูกทุกบรรทัด

## กับดัก CPA — จุดที่คมที่สุดในโจทย์

ตัวอย่างของเจ้าของเอง เข้ารหัสเป็นเทสต์แล้ว:

```
งบ 70,000 · จ่ายเข้ามา 100 คน · ซื้อสินค้าหลัก 5 คน
→ CPA        =    700 บาท   (ดูดีบน Ads Dashboard)
→ CAC จริง   = 14,000 บาท   (แพงกว่า 20 เท่า)
→ verdict: trap
```

🔴 และกรณีที่อันตรายกว่า: **ซื้อสินค้าหลัก 0 คน ⇒ `verdict: 'trap'` ไม่ใช่ `'ok'`**
เพราะ CAC หารไม่ได้ — เป็นสถานะที่ **CPA สวยที่สุดและแย่ที่สุดพร้อมกัน**
(ระบบคืน `coreCac: null` ห้ามแกล้งคืนตัวเลข)

⇒ เลิก optimize เฉพาะ CPA · ต้องดู **ต้นทุนต่อลูกค้าที่ได้ผลลัพธ์จริง**

## สถานะจริงวันนี้ — ทุกตัวชี้วัดคืน `unavailable`

ลูกค้าจ่ายจริง = **0 ราย** ⇒ ตัวชี้วัดทั้ง 8 ตัวคืน `null` และ `showAsActual() = false` ทุกตัว
**นี่คือพฤติกรรมที่ถูกต้อง ไม่ใช่บั๊ก** — `0` กับ "ยังไม่มีข้อมูล" ต้องไม่ปนกัน

**ด่านลงทุนค้างที่ Gate 0**: ยังไม่มีลูกค้าที่จ่ายเงินจริง
และ `canRelease` เป็น `false` **เสมอ** ทุกสถานะ — ระบบเสนอได้ ปล่อยเงินเองไม่ได้

### ต้นทุนจริงต่อแพ็ก (คิดที่เพดาน token เต็ม · worst case Sonnet 4.6)

| แพ็ก | ราคา/เดือน | เพดาน token | ต้นทุน | margin |
|---|---|---|---|---|
| starter | 790 | 1.5M | 454 | **42.6%** ✅ |

### ข้อ 2 — `12,000/ปี` คือแพ็กใหม่ หรือ growth ลดราคา?

🔴 **growth ลดราคาเหลือ 12,000/ปี ทำไม่ได้** — ไม่ใช่ความเห็น แต่คำนวณได้:

```
12,000/ปี = 1,000/เดือน
ให้ token เท่า growth (3M) → ต้นทุน 907 → margin 9.3%   ❌ ต่ำกว่าเกณฑ์ 32%
growth รายปีที่ต่ำสุดที่ยังผ่านเกณฑ์ ≈ 16,020 บาท/ปี   (จากเต็ม 17,880 = ลดได้ ~10% เท่านั้น)
```

🟢 **12,000/ปี เป็น "แพ็กใหม่ระดับกลาง" ได้** — ถ้าเพดาน token ต่ำกว่า growth
(ที่ 1,000/เดือน + token 1.5M → margin **54.6%** ผ่านสบาย)

⚠️ แต่ **ขายเป็น "ส่วนลด starter" ไม่ได้** — starter รายปีปกติ = 9,480 ⇒ 12,000 **แพงกว่า 27%**

กลไก: `annualPricing.test.ts` ล็อกคำตอบนี้ไว้ · ราคาใหม่ทุกตัวต้องผ่าน `meetsMinMargin()` ก่อนประกาศ

### ข้อ 1 — `1,990` เปลี่ยนบทบาทเป็นประตูหน้าไหม?

🔴 **คำถามนี้ตั้งผิดนิดเดียว** — กฎที่ freeze ไว้ (`AUDIENCE.whyNotSideDoor`) เขียนว่า:

> *"นำด้วย **ISO** = แข่งกับบริษัทแม่ตัวเอง"*

⇒ กฎห้าม **สาร** ไม่ได้ห้าม **ราคา** · การมีสินค้าจ่ายครั้งแรกราคา 1,990 ที่เป็น **เรื่องธุรกิจ**
ไม่ขัดกฎเลยแม้แต่น้อย · สิ่งที่ขัดคือการยก **ISO Readiness Pilot** ขึ้นเป็นประตูหน้า

**แต่ข้อเสนอที่ดีกว่าทั้งสองทาง**: บันไดที่ต้องการ **มีอยู่แล้วและ margin ผ่านแล้ว**

```
Paid Entry  = starter 790/เดือน   (margin 42.6%)
Core        = growth 1,490/เดือน  (margin 39.1%)
```

🔴 **เหตุผลที่รายเดือนชนะรายปีในเฟสนี้** — มาจากโจทย์ของเจ้าของเอง:
ความเสี่ยงสูงสุดคือ *"ซื้อแล้วไม่จ่ายรอบสอง"* ⇒ **รายปีกลบสัญญาณนั้นไป 12 เดือน**
`Gate 4` (cohort renewal มีหลักฐาน) จะเลื่อนออกไปเต็มปี · รายเดือนให้สัญญาณทุก 30 วัน

⇒ **ข้อเสนอ: ใช้บันไดที่มีอยู่เป็น Economic Flywheel ก่อน · ยังไม่สร้างแพ็กใหม่
จนกว่าจะผ่าน Gate 3 (มีหลักฐานการแปลงเป็นลูกค้าหลัก)**
— ไม่ต้องสร้างอะไรใหม่ · ไม่แตะกฎ `sideDoor` · และรู้ผลได้ใน 30 วันแทน 12 เดือน

🔴 **แก้คำของผมเอง (10 ก.ย. 2569)** — ประโยคเดิมเขียนว่า *"ยังไม่สร้าง…หรือรายปี"*
**ผิด · รายปีขายอยู่แล้ว**: `access.ANNUAL_MONTHS_CHARGED = 10` (จ่าย 10 ใช้ 12 ≈ ลด 16.7%)
และ `Billing.tsx` โชว์ให้ผู้ใช้ซื้อได้จริง ⇒ ผมตอบคำถามเรื่องรายปีทั้งหัวข้อ
โดยไม่ได้เปิดดูว่ารายปีมีอยู่แล้วหรือยัง — ดู §ราคารายปีที่ขายอยู่จริง ด้านล่าง
