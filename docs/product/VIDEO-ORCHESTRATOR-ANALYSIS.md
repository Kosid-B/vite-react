## คำตอบสั้น

**ทำ — แต่ไม่ใช่แบบที่วาดมา** ต้องเปลี่ยน 2 จุด ไม่งั้นจะเป็นเครื่องที่แพงและแก้ปัญหาที่เราไม่ได้มี

| จุดที่ต้องเปลี่ยน | ที่วาดมา | ที่ควรเป็น |
|---|---|---|
| **ใครใช้** | เครื่องหลังบ้านให้ *เรา* ผลิตคอนเทนต์ | **ฟีเจอร์ที่ลูกค้า SME ใช้เอง** — นี่คือทั้ง PLG และวงจรไวรัลในตัวเดียว |
| **ขายอะไรก่อน** | วิดีโอ | **บท (hook/script/storyboard) ก่อน · วิดีโอเป็นของเสริม** — ต้นทุนต่างกันหลายพันเท่า |

## 1) ทำไมถึงบอกว่า "แก้ปัญหาที่เราไม่ได้มี"

🟢 **หลักฐาน**

| ตัวเลข | ค่า | แหล่ง |
|---|---|---|
| คลิป YouTube 1 ตัว | **942 วิว · คงผู้ชม 89%** · ผู้ติดตาม **0** · แทบไม่มีใครกดออกไปเว็บ | CLAUDE.md บรรทัด 54 (วัดจาก YouTube Studio) |
| คนจาก social เข้าเว็บ (11 วัน) | **32 คน** → กด CTA **1** → สมัคร **0** | `landing_funnel` |
| ผู้เข้าชมทั้งหมด | 78 คน/11 วัน ≈ **50 คน/สัปดาห์** | `landing_funnel` |

**อ่านตรง ๆ**: คนดูคลิปเราจนจบ (89% คือสูงมาก) แต่**ไม่กดออกมา**
⇒ เราไม่ได้ขาด "สายตา" เราขาด **"สะพานจากสายตา → เว็บ"**

⚠️ กฎของโปรเจกต์เอง (`growthPdca.ts:33`) บอกว่าคอขวดคือ *reach* — **ถูก แต่ต้องอ่านให้ครบ**
`bottleneckOf()` นับ *ผู้เข้าชมเว็บ* ไม่ใช่ *ยอดวิว* · เรามีวิวเยอะ แต่วิวไม่กลายเป็นคนเข้าเว็บ
⇒ **ผลิตคลิปเพิ่ม 10 เท่า = คูณศูนย์ด้วย 10** ถ้าสะพานยังไม่มี

🟢 มีหลักฐานตรงอีกชั้น: `quickcheck_submissions` = **0 แถวใน 11 วัน** (ผมพิสูจน์แล้วว่าท่อวัดไม่พัง
โดยเรียก RPC เป็น role `anon` จริงแล้ว rollback) ⇒ แม้แต่คนที่ *มาถึงเว็บแล้ว* ก็ยังไม่ได้ของ

## 2) แต่ทำไมถึงบอกว่า "ทำ"

เพราะถ้าเปลี่ยน **ใครใช้** มันไม่ใช่เครื่องผลิตคอนเทนต์อีกต่อไป — มันกลายเป็น **3 อย่างพร้อมกัน**

### ① เป็น "อาฮ่า" ที่แรงกว่าของเดิมมาก
ตอนนี้ประตูหน้าคือ *"คำนวณต้นทุน"* 🟢 ผลจริง: 78 คน · ใช้จริง **0 คน**
*"ทำคลิปโปรโมตร้านกาแฟให้หน่อย"* คือสิ่งที่เจ้าของร้านอยากได้แต่ทำเองไม่ได้ — จับต้องได้และเห็นผลทันที
(ตรงกับกลุ่มที่ยืนยันแล้ว: **เจ้าของธุรกิจที่ขายอยู่แล้ว 35–65** ซึ่งทำคลิปเองไม่เป็น)

### ② เป็นวงจรไวรัลตัวแรกที่เรามีจริง
ทุกคลิปที่ SME สร้าง → เขาเอาไปโพสต์ในเพจ/TikTok ของเขาเอง → **มีลายน้ำ + ลิงก์ของเรา**
⇒ ลูกค้า 1 คน = ช่องทางหาลูกค้าใหม่ 1 ช่อง
**นี่คือของที่แก้คอขวด reach จริง** ต่างจากการที่เราผลิตคลิปเองเพิ่ม (ซึ่งยังติดสะพานเดิม)

### ③ เป็น PLG เต็มรูปแบบ
ผู้ใช้ได้คุณค่าเองโดยไม่ต้องผ่านคน · และ **dynamic** ตามที่ระบบรู้เกี่ยวกับเขา:
ถ้าเขากรอกเครื่องคำนวณไว้แล้ว ระบบรู้ว่าขายอะไร ราคาเท่าไร กำไรเท่าไร
⇒ hook ของคลิปเขียนจาก**ตัวเลขจริงของเขา** ไม่ใช่เทมเพลต (ตรงกฎ `dynamic-plg`)

## 3) ทำอย่างไรให้มีประสิทธิภาพทั้งระบบ

### 3.1 ขาย "บท" ก่อน "วิดีโอ" — ข้อนี้สำคัญที่สุดเชิงต้นทุน

```
Goal → ICP → Pain → Angle → 3 Hooks → 3 Scripts → 3 Storyboards   ← ต้นทุน = text ล้วน (ถูกมาก)
                                                        ↓
                                                   3 Videos        ← ต้นทุนกระโดดหลายพันเท่า
```

🟢 โปรเจกต์มีกฎ `MIN_MARGIN_PCT = 30` (`tokenEconomics.ts:25`) — ทุกแพ็กต้องมีกำไร ≥30% แบบ worst case
🟡 ผมยังไม่รู้ราคาจริงของ Veo/Runway ณ วันนี้ (**ห้ามเดาแล้วเล่าเหมือนรู้**) — แต่โครงสร้างชัดว่า
**บทเกือบฟรี · วิดีโอไม่ฟรี** ⇒ ให้บทฟรี (อาฮ่า) แล้วคิดเงินที่การเรนเดอร์

⇒ **ส่วนที่ให้คุณค่า 80% ราคาเกือบ 0** และมันใช้ของที่เรามีอยู่แล้วทั้งหมด
(`agent-run` · `ai-assist` · โควตา token · `commentReply.ts` · `contentLinkContract.test.ts`)

### 3.2 อย่าสร้าง Provider Router 4 ตัวตั้งแต่แรก
diagram มี `Future OpenAI Video API` / `Future Provider` — 🔴 **นี่คือของที่ยังไม่มีอยู่จริง**
สร้าง **interface + provider เดียว** พอ · router ที่รองรับ 4 เจ้าโดยยังไม่เคยยิงจริงสักเจ้า
= โค้ดที่ไม่มีใครตรวจได้ว่าถูก (บทเรียนข้อ 13 `shipped-not-written`: เครื่องมือไม่มีตัวไหนตรวจว่าโค้ดถูก *เรียกใช้*)

### 3.3 Cost Guardrail ต้องอยู่ฝั่ง server เท่านั้น
🟢 diagram คุณมีข้อนี้แล้ว ✓ — ย้ำเพราะโปรเจกต์เคยพลาดแบบเดียวกัน
(`activateFromSlip` เคยเปิดแพ็กฝั่ง client = อัปรูปมั่วก็เปิดฟรี → ย้ายไป `verify-slip` ฝั่ง server)
เพดานอยู่ฝั่ง client = แก้ด้วย devtools ได้ ⇒ ค่าใช้จ่ายบานโดยไม่มีใครรู้

### 3.4 schema ต้องบังคับให้วงจรปิด ไม่ใช่แค่เก็บไฟล์
ที่คุณให้มา 4 ตารางครอบ ①Plan ②Do ③Check ครบแล้ว ผมเสนอเพิ่ม 3 อย่างให้ ④Act ทำงาน:

| เพิ่ม | ทำไม |
|---|---|
| `video_campaigns` (goal/icp/pain/angle + **destination_url**) | 3 hooks ต้องมาจาก angle เดียวกันถึงเทียบกันได้ · และ `content-link-contract` บังคับว่าปลายทางต้องมีตั้งแต่ตอนวางแผน |
| `video_projects.parent_id` + `change_reason` (**บังคับด้วย CHECK**) | Version B ต้องบอกได้ว่าเปลี่ยนเพราะตัวเลขไหน ไม่งั้นคือการเดาที่ดูเหมือนการทดลอง |
| `unique (provider, provider_job_id)` | กัน webhook ยิงซ้ำแล้วคิดเงินซ้ำ |

ร่าง SQL เต็มอยู่ที่ `scratchpad/draft-0066_video_orchestrator.sql` — **ยังไม่ apply รอคุณตัดสินใจ**

## 4) เชื่อมกับการตลาดยังไง

```
SME ใช้ฟรี 1 คลิป
      ↓
โพสต์ในเพจ/TikTok ของเขาเอง (มีลายน้ำ + ลิงก์เรา)
      ↓
คนของเขาเห็น → กดลิงก์ → มาถึงเว็บเรา   ← สะพานที่เราขาดอยู่ตอนนี้
      ↓
เจอ "ทำคลิปให้ร้านคุณฟรี 1 คลิป"
      ↓
สมัคร → ใช้ฟรี 1 คลิป → วนซ้ำ
```

🟢 **วัดได้จริงด้วยของที่มีแล้ว**: ลิงก์ในลายน้ำติด `utm_medium=vidloop` + `utm_content=<generation_id>`
⇒ `landing_funnel.by_medium` (migration 0065 ที่ apply ไปแล้ว) ตอบได้ว่า **คลิปตัวไหนพาคนมากี่คน**
⇒ `video_metrics` ปิดวงจร: คลิปไหนได้ลูกค้าจริง → AI เอาไปเขียน Version B

## 5) ลำดับที่ควรทำ — เฟส 0 คือของที่ผมยืนยันที่สุด

| เฟส | ทำอะไร | ต้นทุน | สิ่งที่ได้รู้ |
|---|---|---|---|
| **0 · พิสูจน์ก่อนสร้าง** | ทำมือให้ SME จริง 5 ร้าน (ไม่ต้องมีระบบเลย) แล้วดูว่า **เขาเอาไปโพสต์จริงกี่ร้าน** | ~0 | คำถามเดียวที่ตัดสินทุกอย่าง: คุณภาพดีพอให้เขากล้าโพสต์ไหม |
| 1 | ชั้นบท (campaign → 3 hooks → 3 scripts → storyboard) ไม่มีวิดีโอเลย | ต่ำ | คนใช้ชั้นบทซ้ำไหม |
| 2 | ต่อ provider เดียว + cost guardrail + Storage + ลายน้ำ/ลิงก์ | กลาง | ต้นทุนจริงต่อคลิป |
| 3 | Metrics → AI วิเคราะห์ → Version B (ปิดวงจร) | กลาง | คลิปแบบไหนได้ลูกค้า |

🔴 **ห้ามข้ามเฟส 0** — ถ้าคลิปที่ AI ทำออกมาไม่ดีพอที่เจ้าของร้านจะกล้าโพสต์ ทุกเฟสที่เหลือคือการเผาเงิน
และเราจะรู้เรื่องนี้ได้ก็ต่อเมื่อเอาของจริงไปให้คนจริงดู ไม่ใช่จากการอ่านสเปกของ provider

⚠️ อุปสรรคของเฟส 0 ที่ต้องพูดตรง ๆ: 🟢 ตอนนี้เรามีผู้ใช้ภายนอก **0 คน** (users 4 · workspaces 2 = ของคุณกับแอดมิน)
⇒ 5 ร้านต้องมาจากเครือข่าย B.Training ของคุณเอง ไม่ใช่จากเว็บ
