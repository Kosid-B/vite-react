# SaaS แทนเอกสาร ISO — สถาปัตยกรรมและข้อจำกัดที่ต้องตัดสินใจก่อน

> **สถานะ: ข้อเสนอ รอตัดสินใจ** — ยังไม่เริ่มสร้าง
> เขียนไว้เพราะการตัดสินใจนี้เปลี่ยนทั้งผลิตภัณฑ์ ราคา และกลุ่มลูกค้า

---

## 1. ข้อเสนอนี้ทำได้จริงไหม — ได้ และไม่ใช่ทางเลี่ยง

**ISO 9001/14001/45001/22301 ข้อ 7.5 ไม่เคยกำหนดว่าเอกสารต้องเป็นกระดาษหรือไฟล์ Word**
มาตรฐานใช้คำว่า *documented information* และระบุชัดว่าอยู่ในสื่อใดก็ได้

ดังนั้นการให้ระบบซอฟต์แวร์เป็นตัวเอกสารเอง **ถูกต้องตามมาตรฐาน** ไม่ใช่การตีความเข้าข้างตัวเอง

**แต่** ข้อ 7.5.2 และ 7.5.3 กำหนดเงื่อนไขที่ระบบต้องทำให้ได้ ไม่ว่าจะอยู่ในสื่อไหน:

| ข้อกำหนด | ระบบต้องมีอะไร |
|---|---|
| ระบุตัวและอธิบายได้ | เลขที่เอกสาร ชื่อ วันที่ ผู้จัดทำ |
| รูปแบบและสื่อเหมาะสม | อ่านได้บนอุปกรณ์ที่ผู้ใช้จริงใช้ (มือถือหน้างาน) |
| ทบทวนและอนุมัติ | **workflow อนุมัติ + ประวัติเวอร์ชัน** |
| พร้อมใช้เมื่อจำเป็น | เปิดดูได้ตอนตรวจ รวมถึงตอนอินเทอร์เน็ตล่ม |
| ป้องกันการแก้ไขโดยไม่ตั้งใจ | **สิทธิ์ผู้ใช้ + audit trail ว่าใครแก้อะไรเมื่อไร** |
| ควบคุมการแจกจ่ายและเข้าถึง | รู้ว่าใครเห็นฉบับไหน |
| **จัดเก็บและรักษาไว้ตามระยะเวลาที่กำหนด** | 🔴 **ข้อที่อันตรายที่สุด — ดูหัวข้อ 3** |

> ถ้าระบบทำ 7 ข้อนี้ไม่ได้ครบ = ไม่ใช่แค่ "ยังไม่ดี" แต่คือ **NC ที่ข้อ 7.5 ทั้งระบบ**

## 2. ปรับกรอบ: ไม่ใช่ "ยกเลิกเอกสาร" แต่คือ "เอกสารกลายเป็นผลลัพธ์ ไม่ใช่สิ่งที่ต้องดูแล"

**สิ่งที่จะพังถ้าตีความว่า "ไม่ต้องมีเอกสารแล้ว":**
- ผู้ตรวจบางรายยังขอไฟล์ PDF เพื่อทำ audit trail ของตัวเอง
- ลูกค้าต้องส่งเอกสารให้ลูกค้าของเขาอีกทอด (เช่น ลูกค้าญี่ปุ่นขอดูระเบียบปฏิบัติ)
- ตอนต่ออายุ/เปลี่ยน CB ต้องมีชุดเอกสารส่งมอบ

**กรอบที่ถูกและขายง่ายกว่า:**

```
เดิม  : เอกสาร = สิ่งที่ต้องเขียน ต้องดูแล ต้องอัปเดต ต้องคุมเวอร์ชัน
ใหม่  : ระบบ = แหล่งความจริงเดียว · เอกสาร = "มุมมอง" ที่ระบบพิมพ์ออกมาเมื่อต้องการ
```

เอกสารไม่หายไป — มัน**เลิกเป็นภาระ** เพราะไม่มีใครต้องมานั่งแก้ Word อีก
อัปเดตข้อมูลในระบบครั้งเดียว เอกสารทุกฉบับที่อ้างข้อมูลนั้นเปลี่ยนตามทันที

**นี่คือคำตอบของปัญหาที่เจอทุกที่:** ระบบ 30–40 ฉบับที่ปีต่อไปต้องไล่อัปเดตทั้งหมด
เพราะแก้ที่เดียวแล้วอีก 12 ฉบับที่อ้างถึงไม่ได้เปลี่ยนตาม

## 3. 🔴 ข้อจำกัดที่ต้องตัดสินใจก่อนขาย — ไม่ใช่เรื่องเทคนิค

### 3.1 ลูกค้าเลิกจ่าย = เสียหลักฐานการรับรอง

นี่คือ**ข้อโต้แย้งแรกที่ผู้ตรวจและลูกค้าจะยกขึ้นมา** และตอบไม่ได้ = ขายไม่ได้

บันทึกตามมาตรฐานต้องเก็บตามระยะเวลาที่กำหนด (มักเป็นปี บางเรื่องนานกว่า)
ถ้าระบบเป็นที่เดียวที่เก็บ แล้ววันหนึ่งลูกค้าหยุดจ่าย หรือเราเลิกให้บริการ
**ลูกค้าเสียหลักฐานทั้งหมด และเสียใบรับรอง**

**ทางเลือกที่ต้องเลือกอย่างน้อยหนึ่งอย่าง:**

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| **ส่งออกอัตโนมัติเป็นชุดเอกสารทุกเดือน** เข้าที่เก็บของลูกค้าเอง | ลูกค้าถือของตัวเองตลอด · ตอบผู้ตรวจได้ทันที | ต้องทำระบบ export ให้ดีตั้งแต่แรก |
| **โหมดอ่านอย่างเดียวฟรีตลอดชีพ** เมื่อหยุดจ่าย | ลูกค้าไม่กลัวติดกับ | เราแบกต้นทุนเก็บข้อมูลตลอดไป |
| ให้ดาวน์โหลดทั้งหมดตอนยกเลิก | ทำง่าย | ลูกค้ายังกลัว เพราะต้องเชื่อว่าเราจะยังอยู่ |

> **ข้อเสนอของผม: ทำข้อแรกตั้งแต่วันแรก** — ส่งออกชุดเอกสารเข้า Google Drive/OneDrive
> ของลูกค้าอัตโนมัติทุกเดือน กลายเป็น**จุดขาย**แทนที่จะเป็นข้อกังวล
> และแก้ปัญหา "ผู้ตรวจขอ PDF" ไปพร้อมกัน

### 3.2 "ISO ทุกมาตรฐาน" ไม่ใช่ขอบเขตที่ทำได้จริง

ISO มีมาตรฐานหลายร้อยตัว เราเชี่ยวชาญจริง 4 ตัว

**สิ่งที่ทำได้และควรพูด:** สถาปัตยกรรมเป็นแบบ *standard-agnostic* อยู่แล้ว
(`isoStandards.ts` เพิ่มมาตรฐานใหม่ = เพิ่มอาร์เรย์ ไม่ต้องแก้ตรรกะ)
แต่**ชุดเอกสารกระชับและสายโซ่ของแต่ละมาตรฐานต้องมีคนที่เชี่ยวชาญจริงเป็นคนจัด**
ซึ่งคือทรัพย์สินของเรา และเป็นสิ่งที่ทำให้ลอกไม่ได้

**พูดว่า** "รองรับ 4 มาตรฐานหลัก และขยายได้" · **ห้ามพูดว่า** "ทุกมาตรฐาน"

### 3.3 เปลี่ยนกลุ่มลูกค้าและคู่แข่ง

| | CEO AI Thailand วันนี้ | ถ้าทำอันนี้ |
|---|---|---|
| ผู้ซื้อ | เจ้าของธุรกิจเล็ก | QMR / ผู้จัดการระบบ / ผู้บริหารโรงงาน |
| ราคา | ฿590–5,900/เดือน | สูงกว่านี้มาก (ต่อผู้ใช้ หรือต่อมาตรฐาน) |
| คู่แข่ง | เครื่องมือ AI ทั่วไป | ระบบ QMS/EQMS ที่มีอยู่แล้วทั้งไทยและต่างประเทศ |
| วงจรขาย | สมัครเอง | ต้องนำเสนอ ทดลองใช้ อนุมัติหลายชั้น |

**ไม่ได้แปลว่าไม่ควรทำ** — แต่แปลว่านี่คือ**ผลิตภัณฑ์ที่สอง** ไม่ใช่ฟีเจอร์ของตัวเดิม
และควรมีชื่อ ราคา และหน้าขายของตัวเอง

## 4. สถาปัตยกรรม — ต่อยอดจากที่มีอยู่แล้ว

### สิ่งที่สร้างไว้แล้วและใช้ต่อได้ทันที

| มีแล้ว | ใช้เป็นอะไร |
|---|---|
| `isoStandards.ts` | ชั้นข้อกำหนด — 4 มาตรฐาน 100 ข้อ พร้อม guide/priority/mandatory |
| `isoDocuments.ts` → `LEAN_SETS` | ชั้นเอกสาร — ฉบับไหนรับผิดชอบข้อไหน |
| `AUDIT_THREAD` | ชั้นตรรกะ — สายโซ่ที่ผู้ตรวจไล่ |
| `CONTEXT_LAYERS` | ชั้นธุรกิจ — BMC → Flow → เมตริก → เอกสาร → ข้อกำหนด |
| `DOC_SKELETON` | โครงเอกสารสำหรับ generate ออกมาเป็นไฟล์ |
| `checkup.ts` | ประเมินสถานะปัจจุบัน → รู้ว่าต้องสร้างอะไรก่อน |
| Supabase + workspace + RLS | ผู้ใช้หลายคน สิทธิ์แยกตามองค์กร |

**เราไม่ได้เริ่มจากศูนย์ — ชั้นความรู้เสร็จแล้ว เหลือชั้นข้อมูลกับ workflow**

### สิ่งที่ยังไม่มีและต้องสร้าง

```
ตารางหลัก (ต่อ workspace)
  processes        กระบวนการ — ชั้นกลางของ CONTEXT_LAYERS ทุกอย่างแขวนอยู่ที่นี่
  risks            ความเสี่ยง/ประเด็น/อันตราย — ผูกกับ process + clause
  controls         เกณฑ์ควบคุม — ผูกกับ risk
  metrics          ตัววัด — ผูกกับ control (นี่คือคำตอบของ "ทำไมถึงวัดตัวนี้")
  records          บันทึก/หลักฐาน — ผูกกับ process + มี retention_until
  doc_versions     เวอร์ชันเอกสารที่ generate + สถานะอนุมัติ
  audit_log        ใครแก้อะไรเมื่อไร (7.5.3 บังคับ)
```

**หัวใจคือความสัมพันธ์ ไม่ใช่ตาราง** — ทุกแถวต้องตอบได้ว่ามาจากอะไรและตอบข้อกำหนดข้อไหน
ถ้าใครสร้าง metric ที่ไม่ผูกกับ control ระบบต้องเตือน เพราะนั่นคือ KPI ลอย ๆ ที่จะเป็น NC ที่ 9.1

## 5. MVP ที่เล็กที่สุดที่พิสูจน์ได้ว่าไอเดียนี้ใช้ได้

**อย่าเริ่มจากสร้างทั้งระบบ** — เริ่มจากชิ้นเดียวที่ถ้าใช้ไม่ได้ ก็รู้เร็ว

### ลำดับที่แนะนำ

| ลำดับ | สร้างอะไร | พิสูจน์อะไร |
|---|---|---|
| **1** | **ทะเบียนกระบวนการ + เมตริก** (ชั้น 2–3 ของ CONTEXT_LAYERS) | ลูกค้ายอมกรอกไหม · กรอกแล้วตอบคำถาม "ทำไมถึงวัดตัวนี้" ได้จริงไหม |
| 2 | ผูก risk → control → metric ให้เห็นสายโซ่ | สายโซ่ที่ออกแบบไว้ใช้ได้กับงานจริงไหม |
| 3 | Generate เอกสาร 1 ฉบับจากข้อมูล (เริ่มที่ "บริบทองค์กร") | ผู้ตรวจรับเอกสารที่ generate ไหม |
| 4 | อนุมัติ + เวอร์ชัน + audit log | ผ่านข้อ 7.5 ไหม |
| 5 | ส่งออกอัตโนมัติเข้าที่เก็บของลูกค้า | แก้ข้อกังวลข้อ 3.1 |

> **ขั้น 1 คือขั้นที่ต้องทำก่อนเสมอ** เพราะทุกอย่างแขวนอยู่กับกระบวนการ
> และเป็นขั้นที่รู้เร็วที่สุดว่าลูกค้าจะใช้จริงหรือไม่

### เกณฑ์ว่าควรไปต่อหรือหยุด

หลังขั้น 1 กับลูกค้าจริง 1 ราย:
- ✅ ไปต่อ ถ้ากรอกครบภายใน 1 สัปดาห์โดยไม่ต้องให้ที่ปรึกษานั่งกรอกให้
- 🛑 หยุดคิดใหม่ ถ้าต้องให้ที่ปรึกษากรอกให้ทั้งหมด — เพราะนั่นคือบริการ ไม่ใช่ซอฟต์แวร์
  และโมเดลรายได้จะไม่ใช่ SaaS

## 6. ความเสี่ยงที่ต้องรู้ตั้งแต่วันนี้

- **ที่ปรึกษากรอกให้ทั้งหมด** = ขายบริการในคราบ SaaS · ต้นทุนต่อลูกค้าไม่ลด ขยายไม่ได้
- **ผู้ตรวจบางรายไม่รับระบบดิจิทัล** = ต้องมี export ตั้งแต่แรก ไม่ใช่ค่อยทำทีหลัง
- **สร้างครบทุกฟีเจอร์ก่อนขาย** = ใช้เวลาเป็นปี แล้วอาจพบว่าลูกค้าไม่กรอก
- **ผูกกับ 4 มาตรฐานที่เราเชี่ยวชาญเท่านั้น** = ตลาดเล็กกว่าที่คิด แต่ป้องกันได้ดีกว่า
  (ดีกว่าอ้างว่าทุกมาตรฐานแล้วทำได้ไม่ดีสักตัว)
- **ข้อมูลลูกค้าเป็นข้อมูลอ่อนไหว** — ทะเบียนความเสี่ยง อุบัติเหตุ ผลตรวจ
  รั่วครั้งเดียวจบทั้งธุรกิจที่ปรึกษา ต้องคิดเรื่องความปลอดภัยตั้งแต่ออกแบบ ไม่ใช่ทีหลัง

## 7. คำถามที่ต้องตอบก่อนเขียนโค้ดบรรทัดแรก

1. **ทำเป็นผลิตภัณฑ์แยก หรือหน้าใหม่ใน CEO AI Thailand** — ผู้ซื้อคนละกลุ่ม ราคาคนละระดับ
2. **เลือกทางไหนในข้อ 3.1** (ลูกค้าเลิกจ่ายแล้วข้อมูลไปไหน) — ตอบไม่ได้ = ขายไม่ได้
3. **มีลูกค้าปัจจุบันรายไหนยอมเป็นรายแรกไหม** — สร้างโดยไม่มีคนใช้จริงคือความเสี่ยงที่สุด
